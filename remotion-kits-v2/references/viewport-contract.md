# 三维视图契约（`viewport`）

片子里的 3D 素材**永远是外部的**：作者在 Blender、网页工具或素材包里做好的东西。
本层回答的不是「怎么做一个 3D 场景」，而是**「怎么让它在 Remotion 里按帧播、怎么编排机位、怎么取景」**。

它是**能力层**，不是内容层：仓库里不会因为这条契约多出任何场景资产。

---

## 1. 是什么、不是什么

| 是 | 不是 |
| --- | --- |
| 一个**宿主**：把不透明的三维渲染器包成 `SceneHost` | 建模 / 材质 / 贴图 / 粒子工具 |
| 一层**编排**：机位与取景都是 `t` 的纯函数 | 一份场景资产库（复用同一份素材本身就错） |
| 一套**准入判据**：能按 `t` 重放的才能进来 | 一条要求素材改写渲染管线的通道 |

判据一句话：**它只决定「怎么看在看什么」，从不生产「被看的东西」。**

## 2. 契约面：三个类型

| 类型 | 谁实现 | 职责 |
| --- | --- | --- |
| `SceneAdapter` | **素材作者**（套件给 `createHost` 外壳，填 5 个零件） | 把外部素材变成 `SceneHost` |
| `SceneHost` | 由 `createHost`（或作者手写）产出 | `advance(t)` 必须 / `setCamera` `setFraming` `targetPos` `resizeTo` 可选 / `dispose()` 必须 |
| `Camera` / `CameraTrack` | 套件（`cameras.ts`） | 机位是 `t` 的纯函数 |

`SceneHost` **不透明**：本层不知道里面有几个物体、有没有阴影、用的是什么渲染器。
这条不是洁癖 —— 它决定了同一个 `<Viewport>` 能同时接自带 `rAF` 循环的整包素材，
和一个只有 `render(t)` 的极简渲染器。

## 3. 准入判据：能按 `t` 重放

一条 3D 内容能不能走 `<Viewport>`，只看这一条。四条可执行的检查：

| 检查 | 做法 | 判据 |
| --- | --- | --- |
| 无历史依赖 | `replayProbe(host, t, read, fps)`：`advance(t)` 取一次；**从 0 起逐帧走过去**再取一次 | 两次读数**完全相同** |
| 多个时刻 | `portingAudit(host, {read, fps})`：在上面那条上扫 `0.5 / 1.7 / 2.9 / 4 / 7.5` 秒 | `failures` 为空 |
| 与渲染一致 | 合成里渲染第 N 帧 vs `still --frame=N` | 逐字节相同（本套件的跟随探针实测第 0 / 57 / 119 帧一致，`2026-10-28`） |
| 不读真实时钟 | 搜素材里的 `performance.now()` / `requestAnimationFrame` / `Date.now()` / `Math.random()` | 一个也不剩（或已被适配器短路） |

⚠️ 第一条的判据**必须是「逐帧走过去」**。写成「`advance(0)` 之后再 `advance(t)`」是**证伪不了**的：
那条路与直接跳只差一次调用，任何「跳过去能自洽」的错都照样通过 ——
按调用次数被阻尼的宿主、只在循环里赋值的宿主，两种错法都骗得过那种写法（红证跑出来过）。
逐帧走过去才抓得住「每次调用累加一步」的积分器；线性等价的 `dt` 累加（`acc += t - last`）
仍然判过，那是对的 —— 它确实可重放。

这份体检也有**抓不到的东西**，别把它当全绿：素材自带时钟属于「不确定」而非「不一致」
（同一 `t` 渲两次比对才看得出）；只在循环里赋的值两条来路都一样地少（只能与原始效果对照）；
第 4–6 条装载项没有「同一 `t` 两次读数」这种判据。

**过不了怎么办**：把它渲成序列帧或视频，用 `MediaStage` 播。机位不能再调，但内容一定能用。

```
能按 t 重放 ──▶ <Viewport>   机位可编排 · 取景可调 · 任意跳帧
        │
        └─ 不能 ──▶ 渲成序列帧/视频 ──▶ <MediaStage>   不可编排，但一定可用
```

典型过不了的三类：按 `dt` 累加的积分器、只在 rAF 循环里赋值的 uniform、靠 `Math.random` 的流。
港口素材**前两类都踩了**，各打一个补丁才达标：

| 症状 | 修法 |
| --- | --- |
| 云的水平漂移写成 `x += speed * dt` | 改成 `t` 的闭式 `x(t) = wrap(x0 + speed * t)` |
| 水面倒影的时间只在 rAF 循环里 `matRefl.uniforms.uT = t` | 单帧分支也补上同一句 |

## 4. 装载清单（六条，都是实测出来的）

| # | 坑 | 症状 | 修法 |
| --- | --- | --- | --- |
| 1 | 素材自带 `rAF` 循环 | 画面由真实时间驱动，`t` 说了不算 | 短路它的循环，或走「只渲一帧」的分支 |
| 2 | 按 `dt` 累加 | 同一 `t` 两次渲染不同 | 改闭式（见上） |
| 3 | 只在循环里做的赋值 | 抽图与播放不是同一个画面 | 单帧分支补齐 |
| 4 | 素材自己驱动相机 | 外部机位被忽略 | 机位从外面下发，别读全局相机 |
| 5 | 画布按 `id` 硬编码 | 多实例抢同一个元素；游离元素直接 `TypeError` | 把 canvas 通过 `HostEnv.canvas` 传进去 |
| 6 | 只调 `renderer.dispose()` | 上下文仍活着，反复挂载会攒到浏览器上限 | 再 `gl.getExtension('WEBGL_lose_context')?.loseContext()` |

另外两条与构建有关的，只有踩过才知道：

- **UMD 进打包器会走 `exports` 分支**，于是 `window.THREE` 不存在。港口素材的第 1 个
  `<script>` 里除了 three 还跟着 `OrbitControls`（写裸 `THREE`），会在**模块求值期**就抛
  `THREE is not defined` —— 必须把 OrbitControls 拆出来、显式把命名空间递进去。
- **一套素材自带一套渲染库**：港口那份自带 three r147（634 KB），而依赖树里是 r186，
  同页面两套并存；整包进展示页会让 bundle 从 697,721 B 涨到 1,465,067 B（**+767 KB**）。
  这正是「场景不资产化」的体积理由。

前三条（1–3）现在有可执行形态：`replayProbe` / `portingAudit`。第 4–6 条没有，
只能真渲染一次比对。**仓库不带外部素材的可运行样例**：那份港口适配器随「场景不入库」
一起撤了，能跑的例子只有占位夹具（`templates/mockScene.ts`）—— 它把契约的每个零件都跑一遍，
包括下面两条实测。

## 5. 机位与取景的分工

| | 回答的问题 | 在哪 | 形态 |
| --- | --- | --- | --- |
| **机位** | 从哪儿看、看哪儿 | `cameras.ts` | `static` / `crane` / `orbit` / `dolly` / `keyframes` / `cut` / `follow`，纯 JSON，可走 props |
| **取景** | 看多大 | `framing.ts` | `perspective(fov)` / `orthographic(orthoHeight)`；`fitDistance` / `fitOrthoHeight` 算「装满画面」 |

两条纪律：

1. **机位不许带状态**。平滑靠**闭环采样**（在 `t`、`t-dt`、`t-2dt`… 上取目标位置加权平均），
   不是「每帧朝目标挪一点」的阻尼 —— 后者会让序列第 N 帧依赖前 N-1 帧。
2. **取景由宿主执行**。宿主的相机是透视还是正交只有它自己知道，本层只把参数算好递进去。

`follow` 是唯一会「回看」的机位：它按 `samples` 在前几帧上取目标位置，所以每帧会多跑
`samples - 1` 次 `advance`。这是纯函数的代价，不是状态。

### 5.1 两条实测（`2026-10-28`，占位夹具 + 640×360 / 30fps / 120 帧真渲染）

夹具把被跟随的主体画成**红点**，所以「跟得准不准」可以按像素量，而不是靠眼睛说「大约在中间」。
下面每一行都是「闭式算出来的像素」与「渲染出来的像素」对照：

| 机位 | 实测 | 闭式 | 说明 |
| --- | --- | --- | --- |
| `follow` `samples: 1` | 离画面中心 `0.00 px`，120 帧误差中位/最大 `0.000 / 0.000 px` | 注视点就是主体，应当在正中 | 逐帧步长 `0.00 px` —— 主体被完全钉住 |
| `follow` `samples: 4` | 滞后 `7.47 px`，误差中位 `0.061` 最大 `0.167 px` | `7.48 px` | 逐帧步长中位 `0.40 px`、接缝 `0.31 px`（≈ 一步，不跳） |
| `follow` `mode: 'radial'` | 恒定离中心 `10.54 px`，步长中位 `0.00 px` | `10.54 px` | 径向模式下主体**在画面里不动**，动的是背景 |
| 目标名不存在（`fallback`） | 120 帧都有主体，误差最大 `0.252 px` | 退回静态注视点 | 不黑屏、不抛 |
| `orthographic` `orthoHeight: 4` / `8` | 像素尺寸 `212×214` / `108×110`，中心 `(320, 180)` | 顶点凸包 `208.1×210` / `104.1×105` + 描边 `4.57 px` | 同一物体像素高度与 `orthoHeight` 成反比：比值 `1.9864`（扣掉描边）对 `2.0000` |

最后一行是这一层最容易「设计过、没验证过」的地方：夹具一开始只读 `fov`，
`orthoHeight` 被静默忽略 —— 参数存在、没人消费、也没有证据。现在它两种取景都实现。

**如果 `<Viewport>` 漏了「回看之后推进回 `t`」会怎样**：同样条件下主体会多滞后
`17.2 px`（`samples: 4`）/ `24.2 px`（radial），与上表的 `7.47` / `10.54` 差得很远 ——
也就是说这一项不是「看起来差不多」，而是**能分辨出来**。

### 5.2 分镜（`shots`）：有建模、缺镜头

场景本身没有镜头时用它。补的不是内容，是**看的方式**，产物是一份纯 JSON：

| 字段 | 意思 |
| --- | --- |
| `subject.center` / `subject.size` | 主体的**世界 AABB**（宽 / 高 / 深，世界单位）。旋转件报**旋转后**的包围盒。⚠️ 量的是包围盒，所以肉眼看到的物体通常比 `fill` 小 |
| `shots[].duration` | 这一镜多少秒（各镜之和应当等于合成长度） |
| `shots[].view` | 起始视角 `{azimuth, elevation}`（度） |
| `shots[].framing.fill` | 主体**投影高度**占画面高度的比例；(0, 1] |
| `shots[].framing.shift` | 主体中心相对画面中心的偏移（±1 = 到边缘），`+x` 右 / `+y` 上 |
| `shots[].move.to` | 这一镜**之内**的运动终点（可带 `fill`）；缺省不动 |
| `shots[].transition.frames` | 从**上一镜末尾**过渡进来的帧数；缺省硬切 |

**取景尺怎么解**：先按「主体过中心、垂直于视线」的一阶几何估一个距离，再在**对数空间二分**
（不是乘比例迭代）找让投影高度恰好等于 `fill` 的距离；然后守宽度 —— 宽度超过 `0.98` 画面宽
就把距离再推远（这时高度占比会**小于**声明值：装不下就得退，这一点写死）。

两个踩过的坑，都留在代码注释里：

- **`shift` 一开，主体就不在光轴上**：按「居中几何」解出来的距离拿到成片上会偏 ——
  实测声明 `0.85` 只渲出 `0.758`（差 `30 px`）。所以求解必须用**真实的、已偏移的相机**去量。
- **相机会进到主体包围球里**（特写）：这时一定有角在相机背后。把它判成「距离非法」会让求解
  在「太近 → 翻倍 → 又太近」之间震荡；正确做法是**只量相机前方的角** —— 特写本来就只看得见一部分。

**实测**（`2026-10-28`，静态长方体主体 1.6×1.1×0.8，640×360 / 30fps 真渲染）：

| 判据 | 声明 | 实测 |
| --- | --- | --- |
| 构图占比 | `fill: 0.55` | 包围盒高 `0.5525`（+0.89 px，差值 = 半个描边） |
| 构图位置 | `shift: 0` | 中心点误差 `(0.00, 0.00) px` |
| 占比 + 偏移 | `fill: 0.72`，`shift: {x: 0.18, y: -0.08}` | `0.7219`（+0.69 px），中心误差 `(-0.10, +0.10) px` |
| 硬切 | 三镜，切点在第 36 帧 | 该帧包围盒高度跳 `126.00 px`，**其余帧最大 1.00 px** |
| 过渡 | 第 69 帧起 15 帧 | 过渡段逐帧最大 `11.00 px`，中位 `0.00 px` |

⚠️ **正交取景下的分镜未实现**：正交里大小由 `orthoHeight` 决定、距离不影响它，取景尺的假设不成立。
现在会按透视解算并 `console.warn`。

## 6. 生命周期

```
挂载 ──▶ build(env) 只调一次 ──▶ 每帧 setCamera → setFraming → advance(t) ──▶ 卸载 dispose()
```

- **建一次**：几何 / 着色器 / 贴图都在挂载时建；每帧只改 uniform。
- **尺寸变化不重建**：转发 `resizeTo(w, h, dpr)`。
- **卸载必须释放**：见装载清单第 6 条。
- **多实例**：一个 `<Viewport>` 一个 WebGL 上下文。浏览器上限十几个，
  所以展示页只在视口里挂载；同屏摆很多个之前先想想是否该合成一张图。

## 7. 已知边界

| 边界 | 说明 |
| --- | --- |
| 不做建模 | 场景内容在仓库外；本层只带一份**占位夹具**（几 KB）：线框立方体 + 一颗绕行的红点，后者就是 `follow` 的目标 |
| 不承诺复用 | 素材按片子走，与文案、影音同一条规矩 |
| 玻璃 / 折射 / 粒子 | 不在本路线：它们不是「一个能被编排的宿主」，真渲成素材 |
| 真 GPU 帧时间 | 展示页实测在 headless（SwiftShader）下悬停 16.7 ms/帧、空闲同值；真 GPU 未测 |
| 多张同屏 | 一个 `<Viewport>` 一个 WebGL 上下文；同屏摆很多个之前先想想是否该合成一张图。这一项**未测**，只有「上限约十几个」这个经验值 |
| 过采样 | 画布缓冲区按设计尺寸 ×dpr 走，`dpr` 夹在 [1,2]；别按显示尺寸的 3 倍渲染（实测过采样 5.7× 的那次就是在为看不见的像素付钱） |
