# 创作流程：一个新类型需求 → 一整套组件

**本文件是主线。** 三层契约（`theme-contract.md` / `master-contract.md` / `component-contract.md`）
说明「做对了长什么样」；本文件说明「按什么顺序做出来」。

| | |
| --- | --- |
| **输入** | 一个现有套件装不下的视频类型：新栏目、新体裁、用户临时点名的形式 |
| **输出** | `kits/<类型>/` —— 这个类型的**差异** ＋ `compose.ts`（资产声明）；原语与组件层演示从内核补入 |
| **前提** | 内核（`kits/kernel/`）在，且**全系统只有一份**。八步落的是**差异**，不是一整份套件 |

> ⚠️ **名字**：`kit-core` 是内核的旧名，2026-10-04 起是 `kits/kernel/`。
> 本文件里的**现状描述**一律用新名；引用历史记录时保留旧名。
> 裁定记录（工作区 `docs/`）：`2026-10-04-T01-分发与归属-裁定.md`、`2026-10-04-T02-类型包挂载-裁定.md`。

起手式很简单：**建目录，只放差异。**

```powershell
New-Item -ItemType Directory "<SKILL_DIR>\kits\<类型>"
# 只建你自己要放东西的那几个子目录：theme/ master/ templates/
# 元件层（components/）、护栏（guards/）、组件层演示（KitShowcase）**不要建** —— 那是内核的
```

然后写那份声明（第 8 步会细说，但一开始就该有）：

```ts
// kits/<类型>/compose.ts
export const COMPOSE = { sources: ['../kernel'] } as const;
```

> 本流程的产物是**一套组件**，不是一支片子。片子是它的顺带产物 —— 顺序颠倒（先赶片、组件随手堆）
> 得到的是一支一次性视频，下次还要重写代码，那正是本框架要消灭的成本。

---

## 八步总览

| 步 | 动作 | 产出 | 关卡 |
| --- | --- | --- | --- |
| 1 | 需求拆解：这类视频每期都在讲哪几种东西 | 信息形态清单 → 版式清单 | **用户确认（最便宜的一道关）** |
| 2 | 定槽 | `LAYOUT_SPECS` 形态的槽表 | 必填槽与溢出策略逐条写明 |
| 3 | 定固定家具 | 扩展内核 `FurnitureConfig` 的字段 | 每期都在的元素才配进家具 |
| 4 | 定主题 | `theme/<id>.ts` + 登记 `theme/index.ts` | **2–3 个方向让用户用眼睛选** |
| 5 | 创作 | `theme/**` → `master/**`（→ 通用件归内核） | 逐项按对应契约 |
| 6 | 造演示合成（**不可省**） | 该套件的 `templates/ShowcaseScenes.tsx` 增场景 | 最坏情况内容 + 抽帧清单 |
| 7 | 抽帧验证 | 验证记录（回写 `kit.md`） | **真的看图** |
| 8 | 入库 | `kits/<类型>/` + `kit.md` + `labels.ts` + `compose.ts` + `catalog.md` | 该类型从此可复用 |

## 1. 需求拆解：先问「讲哪几种东西」，不要问「要什么组件」

**问法很关键。** 用户描述需求时说的是内容（「我要做每日新闻」），不是组件（「我要一个进度条」）。
中间那层转换是本流程的核心动作：

> **这类视频每期都要讲的每一种「信息形态」→ 一个版式。**

| 用户说的 | 真正的信息形态 | 版式 |
| --- | --- | --- |
| 「每天开个头」 | 立住主题的一句话 + 日期期号 | 封面 |
| 「头条要说清前因后果」 | 序号 + 标题 + 两三行摘要 | 头条 |
| 「后面还有几条快的」 | 一个标题 + 若干条 | 清单 |
| 「有个数字要吓人一跳」 | 数字主体 + 单位 + 它是什么 | 数据 |
| 「引一句官方说法」 | 引文 + 出处 | 引述 |
| 「最后收个尾」 | 一句话 + 下期预告 | 收束 |

### 定层：什么进套件、什么留在调用处

拆解时每一条都过**两件事** —— 它决定这东西是**写一次**还是**每期重写**，以及**谁维护它**：

| 维度 | 取值 | 它回答什么 |
| --- | --- | --- |
| **① 资产类别** | 主题 · 皮 · 版式 · 母版 · 原语 · 家具 · 夹具 | 这是**什么资产** |
| **② 维护归属** | **内核**（全系统一份）· **类型包**（这个类型专属）· **项目**（这一部作品／这个工程） | **谁持有并维护它** |

⚠️ **两个维度不是一套互斥分类**：主题与皮**也可以由项目维护**，版式也可以在项目里现搭 ——
T01 的版本化源码分发就是让工程副本可改。⇒ **判据落在复用需求上，不落在类别名上。**

| 常见情形 | 资产类别（①） | 常见归属（②） |
| --- | --- | --- |
| 这类视频**每一期**都有的长相？（色板 / 字族 / 字阶 / 安全区 / 间距 / 动效签名） | 主题 | 内核 / 类型包 / **项目** 都可能 |
| 常用外观的预设描述 | 皮 | 同上 —— **项目也可以维护自己的皮** |
| 这个**类型**每一期都有的形？（版式 / 家具 / 槽） | 版式 / 家具 | **这个类型包**（`master/**`） |
| 这个形**别的类型也要**？（排版、布局、基础动效） | 原语 / 机制 | **内核**（`kits/kernel/`）—— 全系统一份 |
| **只有这一期**这样？（场景 / 内容 / 摆法 / 具体时序值） | 内容 | **项目（调用处）** —— 不写进套件 |

> ✅ **依据（2026-10-05 对齐，不是候选）**：架构基线文档 §2 术语（「形」拆成三个对象、简称的含义）・
> §3 **A01**（结构基线）・T01 §2 术语与 §5。上表第四行「通用件归内核」由 T01 的
> 「内核只有一份」直接推出来。

**简称的准确说法：共同机制集中维护，作品输入由项目持有。**
旧的「创作在外（只有值）· 形在内（写一次）· 系统只校验不持有」容易被读成
「创作项目只能填值、每段 JSX 构图都得进类型包」—— 架构基线文档 §2 **明确不这么用**，已改。

- **「只有这一期这样」的东西不要写进套件。** 内容、分镜表、怎么摆、这期用多少毫秒入场 ——
  写进套件之后，套件就变成堆放往期记录的**信箱**，而每期的形态本来就不一样；
- **系统的活是校验，不是持有**（旧句「系统只校验不持有」说的就是这一面）：套件只校验不变量
  （槽、契约、覆盖率），**不持有**「必须这么摆」的规定 —— 摆法是调用处的事；
- 反向判据（第 8 步会用）：**同一个形写第二遍，就是该进套件的信号**；
- 拿不准时问一句：**下期做同类视频，这个东西我要不要再写一次？** 要 → 套件，不要 → 调用处。

做法：

- **横向扫一遍这类视频的 3–5 期真实内容**（或让用户给几期样例），把反复出现的信息形态列出来；
- 每种形态落成一个**有名字**的版式，名字取自形态而不是外观（`timeline` 比 `left-line-list` 好）；
- 上游有 `BRIEF.md` 时先读它的 `genre` / 受众 / 时长，**不要重新问一遍**；
- 顺手记下**这类视频的极端情况**：最长标题多长？最多几条？数字最大几位？第 6 步要用。

**产出**：信息形态清单（每项 = 形态 + 一句话 + 建议版式名 + 极端情况）。

### 关卡：这一步必须给用户确认

这是整个流程里**最便宜的一道关** —— 一份清单，几分钟就能看完；错了改清单只改几行字。
跳过它的代价是：写完 6 个版式、抽完 24 张帧，才发现第 3 个版式对应的是用户根本不需要的形态。

> **不要在没确认信息形态之前就开始写代码。** 这是本流程唯一一处强制暂停。

## 2. 定槽：每个版式声明它装什么、装不下怎么办

对第 1 步的每个版式，逐个槽定四项，照着 `master/types.ts` 里 `LAYOUT_SPECS` 的现成形状写：

| 项 | 取值 | 判断法 |
| --- | --- | --- |
| `name` | 槽名 | 场景里会怎么写它 |
| `kind` | `text` / `lines` / `number` / `meta` | 内容形状 |
| `required` | 必填 / 可选 | **缺了这期就不成立** → 必填 |
| `overflow` | `fit` / `fit-n-lines` / `clamp` / `none` | 见下 |

溢出策略的选择规则（`master-contract.md` 第 5 节）：

- **必填槽 → `fit-n-lines`**：必须完整显示，所以缩字号；
- **可选槽 → `clamp`**：显示不完没关系，截断即可；
- **短而固定的 → `fit`**：缩到一行放得下；
- **本来就不会溢出（如两位序号）→ `none`**，不要白测。

可选槽缺省时**版式必须优雅降级，不留空洞**（`master-contract.md` 第 4 节）。

**产出**：写进 `master/types.ts` 的 `LAYOUT_SPECS` 条目 —— 它是机器可读的，后续流程靠它而非靠猜。
⚠️ 只写**这个类型特有**的版式：内核那 6 个通用版式的槽契约在内核的 `master/types.ts` 里，
`LAYOUT_SPECS` 用一个**自己的** `LayoutName` 联合（只含本类型的版式名）。

## 3. 定固定家具：这类视频每期都在的元素

**家具 = 整片常在、由母版渲染一次、不参与场景入场动效的元素。**

对这类视频问一句：**哪几样东西每期都在？**

| 候选 | 是不是家具 |
| --- | --- |
| 报头（栏目名） | ✅ 每期都在 |
| 期号 / 日期 / 来源 | ✅ 每期都在 |
| 进度（当前第几段 / 共几段） | ✅ 整片级持续动效 |
| 页脚规则线 + 左右小字 | ✅ 版面的收边 |
| 本期头条的标题 | ❌ 那是**内容**，属于场景 |
| 只在一期出现的插画 | ❌ 属于那一期的场景 |

做法：

- **扩展**内核的 `FurnitureConfig`（`import type {...} from '../../kernel/master/types'` 再 `&`），
  **新字段全部可选** —— 不传就不渲染那件家具；
- 家具在 `master/furniture/` 下各一文件，位置由**边距常量**固定，**必须完全落在安全区内**；
- 家具与内容区**不得重叠**，且给家具让位**不能用 `padding`**（绝对定位的子元素不会被父元素 padding 挤开，
  见 `master-contract.md` 第 2 节的三条陷阱）；
- 家具字号一律用母版的 `box.scale`（`Math.min(width, height) / 1080`）。

**产出**：`FurnitureConfig` 的扩展字段表 + `master/furniture/` 下的实现。

## 4. 定主题：视觉身份，让用户用眼睛选

主题是**唯一能整包替换的一层**：换主题不换版式，换版式不换主题（`theme-contract.md`）。

做法：

- 照 `theme/<id>.ts` 复制改一份，**七个身份维度都要动**（`color` / `font` / `type` / `safe` / `space` /
  `motion` / `graphic`）—— 只改 `color.accent` 不叫新主题，叫同一主题的变体；
- **用户没有规范时，给 2–3 个明显不同的方向让他用眼睛选**，而不是问「你要什么颜色」。
  例：深色现代 / 宣纸楷书 / 等宽终端 —— 一眼就能分辨，也一眼就能否决；
- 必须登记进**本套件** `theme/index.ts` 的三处（`ThemeId` / `THEMES` / `THEME_IDS`），
  且 `theme.name` 与注册 id 完全一致；
- **每个字段都必须有消费者**：声明了没人读的字段（`motion.damping` 那类）要么接上，要么删掉；
- **不许 import 内核的主题过来改** —— 那是分叉的来源。
  （`ThemeProvider` / `useTheme` / `Theme` 类型**要**从内核 re-export：全系统只有**一个** context，
  类型包复制第二个，原语与版式就会读到两份主题。）

**验收判据（`theme-contract.md` 第 6.3 节）**：加这套主题前后，`master/**` + `guards/**` + `components/**`
必须逐条一致 —— **换主题时版式 0 行改动**。这条不通过，说明主题层没封住。

**产出**：`kits/<类型>/theme/<id>.ts` + 登记。

## 5. 创作：媒体层的顺序是硬顺序

**先 `theme/` → 再 `master/`（家具 + 版式）→ 通用件归内核。**

为什么必须是这个顺序：

- 版式**强制消费主题**（色 / 字阶 / 间距 / 图形语言从 `useTheme()` 取，几何从 `useMasterBox()` 取）；
  主题没定就写版式，只能写死色值 —— 那就是硬编码，第 7 步的哈希比对必然不通过；
- 组件是**被版式使用**的叶子；先想组件会得到一个「组件堆」，而不是一套版面。

各层照各自契约走：

| 层 | 契约 | 最容易漏的 |
| --- | --- | --- |
| 主题 | `theme-contract.md` | 只改一个维度、字段没人消费、主题名与 id 不一致 |
| 母版（家具 + 版式） | `master-contract.md` | 用 `padding` 让位、`width/1080` 缩放、可变长文本槽不过护栏 |
| 原语（**在内核里加**） | `component-contract.md` + `authoring.md` | 颜色 / 字族写死、多分量插值单位不一致、`transition` 做动画 |

版式写完后**逐个登记进本套件的 `LAYOUT_SPECS`**（第 2 步的表就是它）。

> 创作过程中若发现**内核或已有套件里的东西需要改**（不是新建），停下来走
> `modification-workflow.md` —— 它管「改已有件」：先定根因层，再按波及面重跑回归。
> **尤其是内核**：改 `kits/kernel/**` 会波及**所有**类型包。

> **要不要先在内核里试做、之后拆出去？** 不必了。类型包第一句就声明了它组合内核，
> 缺的层从来源补入 —— 所以从第一天起就能直接建在 `kits/<类型>/`，
> 不会出现拆分前那种「先在别处长大、再搬一次」的返工。

**产出**：`kits/<类型>/theme/**`、`master/**`；（若发现需要新原语）内核的 `components/**`。

## 6. 造演示合成（**不可省**）

把第 1 步记下的极端情况做成场景，加进该套件的 `templates/ShowcaseScenes.tsx`：

- **该套件的演示合成是这套组件唯一的验证载体。** 没有场景，就没有任何被验证过的机会 ——
  写在代码里但从未渲染过的版式，等于不存在；
- 用**最坏情况内容**，不是好看的内容：最长标题、最多条目、最大数字、**空的可选槽**；
  好看的演示内容会掩盖溢出，而溢出正是固定时长 + 变长内容的主要死法；
- 场景加在 `ShowcaseScenes.tsx` 里，母版演示与**所有主题**的演示会一起覆盖到它 ——
  这就是「换主题不换版式」能顺带被验证的原因；
- 每个 `<Sequence>` 都给 `premountFor` 与**硬编码 `name`**；
- **场景中点帧号记下来**，它是第 7 步要抽的帧。
- **每个 prop / 槽分支都要各摆一遍** —— 这不是口号，**生成器会校验它**
  （`showcase/generate.ps1` 的夹具分支覆盖自检：`lines` 槽有/无主字段逐版式查、
  可选槽与家具字段「从不缺省」聚合成一条，走 `NOTE` 通道）。
  只摆一条分支，另一条就是**静默**的 —— `ListLayout` 漏解析 TAB 那个缺陷，
  正因为夹具里从来没写过带主字段的条目，才在展示页里完全看不见
  （硬规则见 `master-contract.md` §4）。

> ⚠️ **组件层演示（`KitShowcase`）不要在这里造，也不要搬一份进来。** 它演示的是内核的 19 个原语，
> 随**元件层**一起由 `compose.ts` 从来源补入。类型包自己那份 `templates/` 只放
> **本套件的母版演示与主题演示**（这两条是本套件自己的时间轴）。

**产出**：新场景 + 抽帧清单（版式 → 帧号）。

## 7. 抽帧验证：`tsc` 全绿不等于对

```bash
npx tsc --noEmit
npx remotion compositions
# 按版式抽帧（每个版式一张），不是按场景抽
npx remotion still <ShowcaseId> out/<版式>-1.png --frame=<该版式中点>
```

- **必须真的看图。** `tsc` 与 ESLint 抓不到渲染期问题：插值单位不匹配、字体回退、对比度不足、
  动画根本没动、WebGL 没开、家具压住内容 —— 全都是「编译通过、渲染才暴露」；
- **按版式抽帧，不是按场景抽**：一个版式可能对应多场戏，场景抽帧会漏掉没被用到的那种排版；
- 清单类版式**额外抽一张末尾帧**（条目全部入场后），否则「后几条来不及出现」查不出来；
- **改了主题或加了主题 → 每个主题 × 每个版式各抽一张**，再做一次哈希比对：
  加主题前后 `master/**` + `guards/**` + `components/**` 必须逐条一致（版式 0 行改动）。
  完整命令见 `theme-contract.md` 第 6 节；
- 结果**记回 `kit.md` 的验证记录**（环境版本 + 命令 + 结果 + 抓到的缺陷）。

> **本框架的每一层都踩过一次「全绿但看图才发现」**：组件层的 `TextReveal` 单位混用、
> 母版的 5 个定位/缩放缺陷、主题层的次要文字对比度。抽帧是唯一可靠的确认手段。

**产出**：验证记录。

## 8. 入库：让下一次不必重写

**类型包只放差异。** 它自己那一份长这样：

```
kits/<类型>/
├── compose.ts      ← 资产声明（下面第 1 条）
├── kit.md          ← 清单
├── labels.ts       ← 只放本套件那几层的中文名
├── theme/          ← 自带主题 + 注册表（provider / useTheme / Theme 类型从内核 re-export）
├── master/         ← 本套件特有的版式 / 家具 / types.ts / MasterFrame.tsx（适配器）
└── templates/      ← 本套件的母版演示与主题演示
```

- **写 `compose.ts`** —— **资产声明**：

  ```ts
  export const COMPOSE = { sources: ['../kernel'] } as const;
  ```

  声明本套件组合了哪些**来源**（相对本目录的套件目录）。生成器照它补入类型包
  **结构上不拥有**的两层：**元件层**（19 个原语 + 声明 + 底色）与**组件层演示**。
  展示页的合并视图靠它成立。
  **工具不认识 `kernel` 这个名字** —— 名字住在声明里，是数据不是规则（T02）。
  ⚠️ 少了它，类型包那一页会**静默**地缺一整片元素墙（实测：页面从 315 KB 掉到 15.7 KB，
  而生成器当时只留一条 NOTE）—— 现在元件层缺失是 **WARN**。
- **不要自带 `components/` 与 `components/specs.tsx`。** 19 个原语是**内核**的，全系统一份。
  这个类型需要一个通用件时，它进**内核**（走 `authoring.md`），不进这里。
  （拆分前每个套件各抄一份 `specs.tsx`，所以类型包也得跟着维护；现在不需要了。）
- **写 `kit.md`**：何时用、这个类型特有的是什么、**为什么内核装不下**、结构、主题清单、
  版式的槽契约、依赖、安装、渲染配置档、已知限制、验证记录；
- **自带母版 / 主题演示合成**：这两条是本套件自己的时间轴，也是它的验证载体。
  组件层演示**不自带**（见第 6 步的警告）。
- **自带主题**（至少一个），且只能通过 `useTheme()` 被消费；
- **写 `labels.ts`** —— 五张表里**只填本套件自己那几层**（版式 / 家具 / 主题，以及自己那几场场景）。
  补入的层（元素 / 组件层场景）由**来源**那份 `labels.ts` 负责 —— 生成器按合并视图取，
  所以类型包这边**不要**为内核的原语再写一遍中文名。
  生成器拿**合并后的**展品清单双向校验：少一个报 WARN、多一个也报 WARN ——
  **缺中文名自己是不会响的**（页面照常渲染，只是那一格退回英文，看起来像「本来就这样」）。
- **更新 `catalog.md` 的「已沉淀」列表** —— 只写真实存在的、抽过帧的，不写没造出来的；
- **重新生成套件展示 web**（`showcase/generate.ps1`）—— 让用户能**看见**这个套件有哪些元素、
  **并且能播**，从而能指着具体元素说「这个要改」。新套件的元素会被自动发现、
  自动变成可播的卡片，**不需要额外为它渲染图**；重跑一次约一秒。
  不重跑，展示页就与套件不同步，而**不同步的展示页比没有更坏 —— 它说谎**。
  生成器会自己对漏项报警（见 `showcase/README.md`）。

> **工程里的微调不用留痕。** 复制进工程的 `src/kits/**` 之后，那个工程为这一支片子做的改动
> **不需要写进任何声明文件** —— T01 裁定 §6 的口径是「不构成 A/B1 的改动 → 无事发生：
> 不裁决、不留痕、不报警」。更新器（`tools/update-kits.ps1`）靠**基线**自己就算得出
> 「这个文件被本地动过」，人工声明那一层**因此被删掉了**（原先的 `FORKS.md`）。
> 它记的「谁改的」是机械事实；至于「这是本片独有还是应该回填」是另一件事，归 `authoring.md`。

### 新类型直接建 `kits/<类型>/`，不要往内核里堆

**内核**（`kits/kernel/`）只放**跨套件通用**的东西：原语、通用版式、通用家具、护栏、母版引擎。
它**不是暂存区**：先堆进去、等积累够了再拆，会带来两次搬迁与一次归属判断的返工，
且期间内核的「通用」定位会被污染。

新类型的主题、母版版式、专属家具**一律直接进它自己的套件**；
**只有一个通用件**（排版 / 布局 / 基础动效这类别的类型也会要的）才进内核。

**「只放差异」不是「少写文件」**：类型包确实比拆分前小得多（一个真实例子：17 个文件 vs 57），
但那是因为它**不再各存一份内核**，不是因为少了功能 —— 运行时通过自己的
`master/MasterFrame.tsx` **适配器**把「内核引擎 + 本套件家具」组合起来，展示层通过
`compose.ts` 把缺的两层补进来。**两处都是显式的，没有隐式的全局状态。**

## 反例清单

- ❌ 没确认信息形态就开始写版式（第 1 步的关卡被跳过）
- ❌ 先写组件再想版面（得到组件堆，不是套件）
- ❌ 主题没定就写版式（只能写死色值）
- ❌ 把「每期都不一样的文案」做成家具
- ❌ 只有好看的内容，没有最坏情况内容
- ❌ 只跑 `tsc`，不看抽帧
- ❌ 按场景抽帧代替按版式抽帧
- ❌ 跳过哈希比对就声称「换主题不动版式」
- ❌ 新类型先堆进内核等以后拆
- ❌ 类型包自带一份 `components/` 或 `KitShowcase.tsx`（那是内核的，复制一份就是两条要各自维护的分叉）
- ❌ 类型包不写 `compose.ts`（展示页会静默缺一层）
- ❌ 类型包为自己的原语再写一遍中文名（那层的家在来源那份 `labels.ts`）
- ❌ 套件没有自己的演示合成，靠别的套件替它验证
- ❌ 把「只有这一期这样」的东西写进套件（内容 / 分镜表 / 这期的摆法）—— 套件会变成堆放往期记录的信箱
- ❌ 调用方显式给的参数被静默改掉（越界后悄悄兜底，画面上看不出来、也没人报）
- ❌ 把这个流程产出的套件说成「已实现」却从没抽过帧
