# 母版契约

**母版（master）= 整片常在的版面骨架**：每帧都在的固定家具 + 一组版式变体 + 每个版式的槽契约。

**主题 / 母版 / 组件三层**；三层不必由同一个套件提供（内核＋类型包的分工见 `SKILL.md` 第一节）。
母版消费主题；组件被版式使用。

契约分**三层**，本文件管母版层：

| 层 | 文件 |
| --- | --- |
| 主题层（长相） | `theme-contract.md`、`kits/kernel/theme/` ＋ 各类型包自己的 `theme/` |
| **母版层（版面）** | **本文件**、`kits/kernel/master/` ＋ 各类型包自己的 `master/` |
| 组件层（原语规则） | `component-contract.md`、`kits/kernel/components/` |

### 内核的引擎 vs 类型包的适配器

母版层**只有一台引擎**（内核的 `master/MasterFrame.tsx`）：带高预留、给家具让位、缩放基准
全在它里面。它**不认识任何类型专属家具** —— 它只提供两个**通用插槽**：`headExtra` / `footExtra`。

类型包要有自己的专属家具时，写一个**适配器**（`kits/<类型>/master/MasterFrame.tsx`），
把那些家具渲染成插槽内容送进内核引擎：

```tsx
<KernelMasterFrame
  {...rest}
  furniture={{
    ...kernelFurniture, // 报头 / 页脚 / 进度… 原样透传
    headExtra: eventStamp ? <EventStamp {...eventStamp} /> : undefined,
    footExtra: source ? <SourceBadge {...source} /> : undefined,
  }}
/>
```

于是两件事同时成立：**内核不认识类型专属家具**（不会反向依赖类型包），
**调用方不感知插槽**（它给的是数据 `furniture={{eventStamp: {...}}}`，不用 import 家具组件）。
带高预留、让位、缩放基准**一个字都不重复** —— 逻辑只有内核那一份。

> **「数据层（内容入槽）」尚未定义** —— 即「内容 → 版式分配」的契约。本技能目前只管到
> 「**组件能装下内容**」；要不要做「内容驱动周期化出片」是另一个决定，不写在这里。
> `LAYOUT_SPECS` 的机器可读性已经为它留好了消费面，但那份契约**现在不存在**。

## 1. 母版的三个要素

| 要素 | 定义 | 不合格的反例 |
| --- | --- | --- |
| **固定家具** | 整片都在的元素：报头、期号 / 日期、进度轨、页脚规则线、logo 位 | 每场戏各写一遍报头 |
| **版式变体** | 有名字的版式：`cover` / `headline` / `list` / `stat` / `quote` / `closing` | 每场戏即兴排版 |
| **槽契约** | 每个版式声明它的槽：必填 / 可选、内容形状、**溢出行为** | 组件只收一个 `text`，溢出没人管 |

三个要素缺一个，就退化成「一堆组件」——那正是构建本技能之前的状态。

## 2. 固定家具

- 在**母版层渲染一次**，绝不在场景里重复；
- 位置由**边距常量**固定，不随场景变；
- 必须完全落在安全区内；
- 内容来自母版 props（`FurnitureConfig`），**不来自场景** —— 母版不接受具体文案；
- 不参与场景入场动效（否则每场戏都会「重新出现」一次）；只允许整片级的持续动效，例如进度轨随帧推进；
- 与内容区**不得重叠**：母版必须为家具预留上下内边距。

> 家具的中文名（展示页上那个 `Masthead · 报头`）**不在 `FurnitureConfig` 里** ——
> 它住在套件根的 `labels.ts`。`FurnitureConfig` 是**内容契约**（每期填什么），
> 中文名是**展示契约**（这一件叫什么），两者寿命不同：家具改了名，内容契约不该跟着动。
> 版式同理（`LAYOUT_SPECS` 只装槽契约）。理由见 `component-contract.md` §5。

### 三条踩过的定位 / 缩放陷阱（硬规则）

1. **给家具让位不能用 `padding`。** 场景是 `<Sequence>`（默认 `layout="absolute-fill"`，即绝对定位），
   **绝对定位的子元素不会被父级的 padding 挤开** —— 内容会从 y=0 开始画，直接压在报头上。
   要用 `top`/`bottom` 定位的内容盒。
2. **用四个 inset 定位内容盒时，必须同时把 `width`/`height` 置 `auto`。**
   `AbsoluteFill` 底层是 `AbsoluteFillElement`，它内置 `width: 100%` / `height: 100%` 并把传入
   style 展开在最后；而 CSS 过约束时 **`width`/`height` 会压过 `right`/`bottom`** —— 于是
   `top:172 + bottom:180 + height:100%` 得到的是 172..1252 的盒子，`left`/`right` 也被
   100% 宽度吃掉。症状是「内容整体下移约一个 padTop，且右侧不再受安全区约束」。
3. **家具的字号必须用母版的 `box.scale`（`Math.min(width, height) / 1080`），不能用 `width / 1080`。**
   后者在 1920×1080 下是 **1.78 倍**，家具字号会涨到比正文还大、并冲出母版给它预留的高度带。
   抽帧实测症状：页脚小字 43px > 正文 32px > 清单条目 29px；报头行 82px > 预留 72px。
   版式层与 `SafeArea` 用同一条规则 —— 三处都必须一致，否则同一帧里两套尺度打架。

## 3. 版式变体

- 一个版式一个文件，并注册进 `LAYOUT_SPECS`（`master/types.ts`）；
- 版式**只负责内容区**：不重复家具、不改画布尺寸、不改安全区；
- 版式的入场动效从**该序列的本地 0 帧**起算，这样放进任何 `<Sequence>` 都对；
- 版式强制消费主题：颜色、字阶、间距、图形语言一律从 `useTheme()` 取，几何从 `useMasterBox()` 取；
- 版式**不得硬编码品牌色、字体名、圆角** —— 那属于主题；
- 版式**不得 import 具体主题文件**（`theme/paper-seal` 之类），只许 `theme/context`；
- 版式里**不得出现 `if (theme.name === …)`** 之类的分支 —— 出现即说明主题层缺字段。

### 本期节奏可覆盖（`staggerInFrames`）—— **已裁定（T06，2026-10-05）**

> **裁定**：**显式值原样生效、不参与收紧**；溢出的代价用**开发期诊断**顶上
> （`guards/diagnostics.ts` 的 `warnIfStaggerOverflows`）。
>
> 判据是实测（`docs/2026-10-05-阶段2-局部实现-实测证据.md` §6）：**同一份 6 条内容、同一个
> 90 帧场景，只有显式节奏不同** —— 默认 7 → **6/6** 全部入场；显式 11 → **6/6**；
> 显式 40 → **2/6**（后四条 opacity 恒为 0）。中间那一列是关键：它证明「场景短」**不是**原因，
> 差异只能归因于「显式值不参与收紧」这条政策本身。

四个会算错开的版式（`ListLayout` · `TimelineLayout` · `StanceLayout` · `MultiStatLayout`）
各有一个可选 prop `staggerInFrames`：**逐条错开的帧数**。

- **省略** → 主题的 `motion.stagger`，并按场景时长**收紧**（`min(主题值, 预算 ÷ (条数−1))`）——
  固定间隔配长清单会让最后几条来不及出现，这是母版层踩过一次的缺陷；
- **给了** → **原样生效，不参与收紧**。理由：收紧是系统对**自己的默认值**做的事，
  不是替调用方改他给的数。代价说清：给大了它会溢出，后果是**可见的**（末条来不及出现）——
  而且现在还会**喊一声**：`lead + (条数−1) × stagger + 入场时长 > 场景时长` 时报出
  「末条第几帧起、第几帧才入场完、超出几帧」。**诊断不改行为**；
- **被否掉的那一侧**是「不溢出优先」（显式值也被压紧）：那不是把静默去掉，而是**换一个方向的静默**
  —— 调用方给的数被悄悄改掉。T06 裁定取前者；
- 四个版式的 `lead` 与入场时长**不是同一个数**（14/18 · 14/20 · 16/22 · 14/22），
  所以诊断要求调用方把这两个数**给进来**，它不替版式假设 —— 这也正是「不统一那两份收紧公式」
  那条既有决定（设计文档 §5.3）在诊断上的直接后果。**两处口径要一起改**；
- 于是「**这一期**想快一点 / 慢一点」是调用处的表达，「**这类片子**默认多快」仍是主题的表达 ——
  这是**定层**里的两类：一个落在**项目（调用处）**、一个落在**主题**。⚠️ 归属与类别是**两个维度**
  （主题本身也可以由项目维护），见 `creation-workflow.md` 第 1 节 —— 两者不冲突。

## 4. 槽契约

每个槽声明四项：

| 项 | 取值 |
| --- | --- |
| `kind` | `text` / `lines` / `number` / `meta` |
| `required` | 必填 / 可选。**可选槽缺省时版式必须优雅降级，不留空洞** |
| `overflow` | `fit` / `fit-n-lines` / `clamp` / `none` |
| `note` | 一句话说明这个槽放什么 |

`LAYOUT_SPECS` 是**机器可读**的 —— 它首先是「这个版式有哪些槽、哪些必填、溢出怎么办」的正式契约；
将来若要做「内容 → 版式分配」，消费的就是它。

### 内容槽与控制参数是两类东西（**硬规则**，T09 裁定 2026-10-05）

版式的 props 上有两类东西，**性质不同**，数「有几个槽」时不能混在一起：

| | 装什么 | 例子 | 进不进 `LAYOUT_SPECS` |
| --- | --- | --- | --- |
| **内容槽** | 这次**要说什么** —— 作品内容 | `title` / `items` / `events` | **进**。注册表回答的就是「这个版式有哪些槽」 |
| **控制参数** | 这次**怎么排** —— 不含任何内容 | `staggerInFrames`（见 §3.1） | **不进**。槽＝内容；把节奏混进去，「这个版式有哪些槽」这句话就不成立了 |

两份名字在代码里只有**一处**：`kits/kernel/master/types.ts` 的 `LAYOUT_CONTROL_PROPS`
（住在内核，因为它跨两侧 —— 内核的 `ListLayout` 与类型包的三个版式都有）。
消费方（场景类型 / 槽声明审计器）**先按它把两类分开，再各自比对**。

⚠️ **不分开就比，会得到「声明与实现不一致」这种看起来像缺陷的读数** ——
T09 那次实测里，四个版式的 `staggerInFrames` 就被当成「注册表漏了四个槽」报了出来，
它长得像证据（有文件、有行号、可复跑），量的是错的那件事。见 `AGENTS.md` 同名那条。

### `kind: 'lines'` 的编码（硬规则）

`lines` 槽的每一条是 `'主字段<TAB>说明'`。**用 TAB 而不是逗号或竖线** ——
文案里出现逗号和竖线是常态，TAB 不会。

三条都要做到：

1. **消费方必须解析它。** 把整条字符串直接交给浏览器，TAB 会被 HTML 塌缩成一个空格，
   主字段与说明的区别在视觉上**完全消失** —— 而且不报错、`tsc` 也全绿。
2. **解析只有一份实现**（套件里的 `master/slots.ts` 的 `splitEntry`），不要在版式里各写一遍 ——
   各写一遍就是「改一处漏一处」，而它恰恰是最容易漏的那一处。
3. **没有分隔符时整条当说明**（主字段为空），版式据此退回**单列整宽**。
   于是「普通清单」与「带主字段的对照清单」能共用同一个版式，
   **两条分支都要在演示合成里各摆一遍** —— 只摆一条，另一条是静默的。

> **一次实测**：真实片子里 `list` 的一段「本地打包 据排查：客户端扫描工作区…」被读成一句话，
> 主字段与说明的区别完全消失。根因不在文案，在于 `ListLayout` 的 `items` 是 `lines` 槽
> 却从未调用 `splitEntry`。**更值得记住的是它为什么没被发现**：那个套件的演示合成里
> 从来没有写过带主字段的条目，所以这条分支在展示页里根本走不到。
> 完整记录见 `kits/hotspot/kit.md` 的验证记录。

## 5. 溢出护栏（硬规则）

**可变长文本槽必须过护栏。** 这是母版唯一的强制测量要求，也是「固定时长 + 变量内容」唯一能安全成立的前提。

三种策略：

| 策略 | 工具 | 适用 |
| --- | --- | --- |
| 缩放到**一行**放得下 | `useFittedFontSize()` | 标题、期刊名、期号、标签 |
| 缩放到 **N 行**内放得下 | `useFittedLines()` | 头条标题、引文 |
| **截断**到 N 行 | `<ClampLines>` | 摘要、次要说明 |

- 护栏**必须设字号上下限**，否则长文本会缩到不可读；
- 依赖 `@remotion/layout-utils`（官方包，版本随 Remotion）—— **测量不能靠猜**；
- 用网络字体时，字体未加载则测量不准，必须先 `waitUntilDone()`；
- 测量与渲染必须用**同一个 `fontFamily` 字符串**；两者都取自 `useTheme()`，
  所以换主题时字号会跟着字族一起重算 —— 这是「换主题不用改版式」还能不溢出的原因；
- **护栏测的宽度必须与文本实际渲染的盒子一致。** 版式里只要还有别的元素与文本**同排**
  （如 `headline` 的序号列），文本盒就比 `contentWidth` 窄 —— 要把那部分宽度**扣掉**再传给护栏，
  并且把这个宽度**同时写进渲染盒**。两件事都要做：
  只扣不写，下次改版式又会重新错开；只写不扣，护栏测的还是旧宽度。
  **症状**：护栏按更宽的盒子选了偏大的字号，浏览器再按真实盒宽**重新贪心折行**，
  于是末行可能只剩一个字 —— 看上去像「断行算法不好」，根因却是这个宽度差。
> **一次实测**：`headline` 的标题断出过孤字「下」。当时的记录把根因写成「贪心断行」，
> 后来才发现真根因是**护栏测宽 ≠ 渲染盒宽** —— 序号列挤窄了标题盒，护栏却按整幅宽度选字号。
> 修法见上面这条规则；完整记录见 `kits/kernel/kit.md` 的验证记录（当时那个目录叫 `kit-core`）。
>
> **又一次实测（分栏版式）**：`list` 的条目**带主字段**时正文列被主字段列挤窄，
> 而护栏仍按 `contentWidth` 测 → 选出偏大的字号 → 浏览器按真实列宽重新折行。
> **同一个根因、第二次出现**，说明这条规则不是「序号列的特例」，而是**任何分栏**的通用约束。

⚠️ **护栏作用的对象是「内容」，不是「调用方显式给的参数」。** 内容可变、没人给它字号，护栏替它兜底；
而调用方**显式给了**字号 / 尺寸 / 时序值时，那个值要么原样生效，要么以**可见**方式失效 ——
不能悄悄改掉（原则出处见 `references/component-contract.md` 第 5 节「显式参数永不静默改变」——
⚠️ 那条**已由 T05 / T04 / T06 落地**，不是候选）。

## 6. 主题与母版的关系

| | 拥有 | 绝不包含 |
| --- | --- | --- |
| **主题** | 色板（含网格线与暗角颜色）、字体族、字阶、安全区与间距标量、家具高度、动效签名、图形粗细与圆角 | 任何布局信息：版式名、位置、槽、顺序 |
| **母版** | 家具、版式、槽契约、内容区盒模型 | 任何具体色值、字体名、圆角 |

**换主题不换版式，换版式不换主题。** 这条是「同一母版配多个主题」的前提，也是本层存在的理由。
硬指标与实测证据见 `theme-contract.md` 第 6.3 节。

## 7. 验证（母版级，比组件级更严）

- **抽帧按版式，不按场景**：每个版式一张，不是每场戏一张；
- 每个版式用**最坏情况内容**：最长标题、最多条目、最大数字、空的可选槽；
- `npx tsc --noEmit` 必须通过；
- **必须看抽帧** —— 类型系统抓不到溢出、抓不到单位不匹配（内核首次验证就踩过：`tsc` 全绿但渲染抛错）；
- 清单类版式要**额外抽一张末尾帧**（条目全部入场后），否则「后几条来不及出现」这类缺陷查不出来；
- **换主题后重跑同一组抽帧**，确认没有色值 / 字体 / 尺度硬编码漏进版式；
- 母版演示与主题演示**共用同一份内容**（`templates/ShowcaseScenes.tsx`），
  这样并排对比时差异只可能来自主题。

## 8. 反例清单

- ❌ 在场景里重复写报头 —— 家具属于母版
- ❌ 版式里硬编码品牌色 / 字体名 / 圆角 —— 属于主题
- ❌ 版式 import 具体主题文件，或按主题名写分支
- ❌ 家具与内容区重叠
- ❌ 家具字号用 `width / 1080`
- ❌ 可变长文本槽不过护栏
- ❌ 护栏测的宽度与文本渲染盒不一致（同排元素占掉的宽度没扣，或扣了却没写进渲染盒）
- ❌ 护栏不设字号下限（长文缩成蚂蚁）
- ❌ 母版里写死具体文案
- ❌ 用「按场景抽帧」代替「按版式抽帧」
- ❌ 为了让某个版式好看而改安全区或画布尺寸
