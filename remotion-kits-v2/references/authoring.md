# 新组件入库流程（新增）

套件要能长大。这份文件定义「往套件里加**一个**组件」的标准动作，保证加进来的东西是**验证过的**、
**可复用的**、**不会拖慢渲染的**。

**本文件是 `creation-workflow.md` 的组件级子过程。** 三者分工：

| 文件 | 管什么 | 什么时候读 |
| --- | --- | --- |
| `creation-workflow.md` | 从一个**全新类型的视频需求**造**一整套**组件（主题 + 母版 + 组件 + 演示合成） | 用户提出新类型时 —— **先读它** |
| **本文件** | 往**已有**套件里加**一个**组件（**新增**） | 套件已经在，只需补一个叶子元素 |
| `modification-workflow.md` | **修改**已经存在的组件 / 版式 / 主题，以及改完按波及面重跑回归 | 要动一个**已经存在**的东西时 —— 读它，不是读本文件 |

造整套时，本文件的步骤 0–2（该不该做成组件 → 归属 → 怎么写）照样适用，但**创作顺序由
`creation-workflow.md` 第 5 步决定：先主题、再母版、最后按需补组件** —— 反过来做会写出硬编码色值的组件。

> **新增与修改的分界**：本文件只管「从没有到有」。一旦目标**已经存在**（哪怕只是改一个默认值、
> 一个宽度、一个色源），走 `modification-workflow.md` —— 那边的核心是「先定根因层」与
> 「按波及面重跑回归」，而本文件的步骤 0（该不该做成组件）对已有件没有意义。

先分清加的是哪一类，验证载体不同：

| 加什么 | 演示 / 验证载体 |
| --- | --- |
| 契约原语（**内核的** `components/`） | **内核的** `templates/KitShowcase.tsx` |
| 母版版式（该类型包的 `master/layouts/`） | 该类型包的 `templates/ShowcaseScenes.tsx`（母版与主题两套演示共用） |
| 主题（该类型包的 `theme/`） | `theme-contract.md` 第 6 节（每版式每主题抽帧 + 哈希比对） |

---

## 步骤 0：先判断该不该做成组件

**做成组件**，当满足任一条：

- 这个视觉元素在**这一支视频里会出现 ≥2 次**；
- 它的实现有**值得隔离的复杂度**（多层结构、多个插值、容易写错的单位）；
- 它**跨视频可复用**（属于某个视频类型，而不是这一支独有）。

**不要做成组件**，当：

- 只出现一次且很简单 —— 直接内联写在场景里更省事；
- 它其实是**内容**而不是**形态**（比如某一句特定的文案）。

判断错成组件的代价：多一层抽象、多一个文件、Studio 时间线多一层嵌套。判断错成内联的代价：复制粘贴、改一处漏一处。

---

## 步骤 1：决定归属哪一层

| 情况 | 去处 |
| --- | --- |
| **任何视频都可能用**（排版、基础动效、布局） | **内核**（`kits/kernel/components/`） |
| 只对**某一个类型**的版式有意义 | 那个**类型包**自己的目录（作为**内部件**，不是契约原语 —— 见下） |

**跨套件通用的组件放内核，绝不要复制到多个类型包里** —— 复制会产生分叉，修了一个忘了另一个。

> **没有「复制一份然后各自维护」这条路。** 内核全系统一份，类型包**不持有元件层**
> （它要的那一层由 `compose.ts` 从来源补入 —— 见 `creation-workflow.md` 第 8 步）。

> ⚠️ **已知边界：一个「类型专属的契约原语」现在没有干净的落点。**
> 元件层是**整层**从来源补入的（`components/` 要么整个是内核的，要么整个是自己的），
> 所以类型包**不能在保留内核 19 个原语的同时再添第 20 个**。今天两个套件都不需要这件事
> （`hotspot` 一个原语都没新增过）。真需要时的两种处置：
>
> 1. 它其实是通用的 → **进内核**，成为第 20 个契约原语；
> 2. 它只服务本类型的版式 → 放在**类型包自己的目录**下、由该类型的版式 import。
>    它**不是契约原语**：不进 `COMPONENT_SPECS`、不进元素墙、不受 `component-contract.md`
>    的「原语」那套要求（但仍受「颜色只从 `useTheme()` 取」这类硬规则约束）。
>
> 第三条路（按**单个原语**组合，而不是整层）不在本文件的范围里 —— 要走那条路，先确认它与
> `compose.ts` 的整层补入相容，别照边角自行决定。

`kits/kernel/` 只放**跨套件通用**的原语，**不要把它当成新类型的暂存区**：先堆进去、等以后拆，
会带来两次搬迁和一次归属返工，期间还会污染内核的「通用」定位（见 `creation-workflow.md` 第 8 步）。

---

## 步骤 2：写组件

严格按 `component-contract.md`。几个最容易漏的点：

- `type Props`，不用 `interface`；props 全 `readonly`；
- 每个数值 prop 注释写明单位（像素还是帧）；
- 入场延迟叫 `delayInFrames`，入场长度叫 `enterDurationInFrames`（**不要**叫 `durationInFrames`）；
- 从本地 0 帧起算；
- 多分量插值的每个分量单位一致；
- 动画 `scale` 加 `output: 'perceptual-scale'`；
- 所有 `interpolate` 写 `extrapolate*`；
- **颜色 / 字族 / 圆角从 `useTheme()` 取，不要写死**（内核里的原语这样 import）：

```tsx
import {useTheme} from '../theme';   // ✅
// import {theme} from '../theme/default';   // ❌ 组件就只会长成那一个主题的样子

const theme = useTheme();
color: color ?? theme.color.ink,
fontFamily: theme.font.family,
```

- **字号默认值保持内联**（Studio 可编辑）。要让字号跟随主题，让调用方显式传 `theme.type.*`；
- 安全区缩放一律 `Math.min(width, height) / 1080` —— 见 `component-contract.md` 第 5 节。

## 步骤 3：在演示合成里加一个场景

**这一步不能省。** 演示合成是验证载体 —— 没有它，这个组件就没有任何被验证过的机会。

- **契约原语 → 在内核的 `KitShowcase.tsx` 里给它一个 `<Sequence>` 场景**
  （类型包不再自带这一份：它由 `compose.ts` 从内核补入，所以内核加了，两个套件的展示页都会看到）；
- **原语还要写进内核的 `components/specs.tsx` 的 `COMPONENT_SPECS`** —— 声明它的 prop、
  **显示语义 `display`**（`inline` / `block` / `container`）、
  **`demoFrame`**（该原语自己的动画完成帧，各原语不同）、
  **`tunable`**（1–3 个「想改 / 能改」的 prop —— 展示页只挂这几个，判据见 `component-contract.md` 第 5 节）
  和一个诚实的演示实例。
  这是**原语视图**的数据来源，也是「声明 vs 实现」漂移检查的对照物 ——
  生成器会拿它比组件源码的 `type Props`，并检查 `display` 合法、`demoFrame` 已声明；
- 版式 → 在该**类型包**的 `ShowcaseScenes.tsx` 里加一个场景（母版演示与**所有主题**的演示会一起覆盖到）；
- 给 `premountFor` 与硬编码 `name`；
- 把**新组件的每个 prop 分支都摆一遍**（比如 `Emphasis` 的 highlight / underline / box 三种都放）。
  ⚠️ **结构分支最容易漏**：`lines` 槽有「带主字段」与「不带」两条，可选槽有「给」与「不给」两条。
  只摆长度上的最坏情况是不够的 —— 生成器会对没演练到的分支报 **NOTE（覆盖缺口）**；
- ⚠️ **演示里摆进去的东西，都会被读成「这个原语的用法」。**
  为了演练某个分支而摆的**陪衬**（第二张卡、第二行、对照组、相邻元素…）必须**一眼能分辨是陪衬**；
  否则看的人会把它当成**必需的**，于是得到一个**假约束**，以为这个原语「甩不掉那一件」。
  **判据：把陪衬删掉，这个原语还成不成立？** 成立的话，它要么能一眼看出是陪衬，
  要么干脆别摆 —— 把那一支留给展示页的元素格（那里本来就定格一帧，更适合摆单件）。
  （实测：`Panel` 的演示摆了第二张卡来演练「压暗」这一支，看的人以为「用这个原语必须带第二张卡」。）
- 场景中点帧号记下来，它是下一步要抽的帧。

## 步骤 4：验证

```bash
npx tsc --noEmit
npx remotion compositions
npx remotion still <ShowcaseId> out/k-new.png --frame=<新场景中点>
```

**必须看抽帧。** `tsc` 抓不到插值单位不匹配、字体回退、对比度不足、动画没动、WebGL 没开这类问题 ——
内核首次验证就踩过一次（`TextReveal` 的单位混用，`tsc` 全绿但渲染抛错）。

- 改了原语 / 版式 → 重跑 `KitShowcase` 与 `MasterShowcase` 的整组抽帧；
- **改的是内核那一层 → 还要重新生成展示页**：每个类型包那一页的元素墙都是从内核补入的，
  不重跑它就与套件不同步（而不同步的展示页比没有更坏 —— 它说谎）；
- 改了主题或加了主题 → 按 `theme-contract.md` 第 6 节跑**每版式每主题**的抽帧，并做一次哈希比对；
- **如果新组件用了 WebGL**（`@remotion/effects` / `three` / 地图），抽帧前先确认 `--gl=angle` 已生效。

## 步骤 5：更新清单

在内核的 `kit.md` 里补（加了原语时）：

- 组件表新增一行（组件名 · 做什么 · 关键 props）；
- **`components/specs.tsx` 里补一条 `COMPONENT_SPECS`**（prop 表 / `display` / `demoFrame` / `tunable` / 演示实例）——
  漏了它，原语视图里不会出现这个原语，生成器也会报 NOTE；
- **内核根的 `labels.ts` 的 `elements` 表里补一条中文名** —— 它只服务展示页
  （`Title · 主标题`），不进 `ComponentSpec`。**缺一条不会自己响**：页面照常渲染，
  只是那一格退回英文。生成器双向校验（少一个 WARN / 多一个 WARN），前提是你重跑了它；
  ⚠️ **这一条写在来源那份里**（内核那份）—— 类型包的 `labels.ts` **不要**再为内核的原语写一遍，
  生成器是按**合并视图**取中文名的；
- 若引入了新依赖，更新「依赖」小节；
- 若渲染要求变了（比如开始用 WebGL），更新「渲染配置档」小节；
- 已知限制：这个组件有什么反直觉的用法或缺陷；
- 验证记录：追加一行实测结果。

## 步骤 6：这个类型还没有类型包时

**建类型包不在本文件里决定**：整套创作（建目录 → 定槽 → 定家具 → 定主题 → 创作 → 演示合成 → 抽帧 → 入库）
走 `creation-workflow.md` 的八步，其中第 8 步逐条列出类型包该有的每一样东西
（`compose.ts` / 自带主题 / 母版与主题演示 / `labels.ts` / `catalog.md` 登记）。

与组件相关的差别只有一条：**需求若只是一个通用件，它进内核**（见步骤 1），不进新类型包。

## 反面清单（不要做的事）

- ❌ 加一个没有在演示合成里出现过、也没抽过帧的组件
- ❌ 把品牌色 / 字体名硬编码进组件体（那属于主题，用 `useTheme()` 取）
- ❌ 让组件 import 某个具体主题文件（组件就再也不能换主题了）
- ❌ 在组件里写 `transition` / `animation` / Tailwind 动画类
- ❌ 用 `width` / `height` 做动画
- ❌ 补间里调 `getBoundingClientRect()`
- ❌ 同一个组件复制到两个套件里（**现在连「类型包自带一份通用原语」这条都没有了**）
- ❌ 在类型包里新建 `components/` 或 `KitShowcase.tsx`（那是内核的层）
- ❌ 新建类型包却忘了写 `compose.ts`（展示页会静默缺一层）
- ❌ 新类型先堆进内核、等以后拆（直接建 `kits/<类型>/`）
- ❌ 在 `catalog.md` 里写入没抽过帧、并不存在的套件
