# 改已有组件 / 版式 / 主题

**新增与修改是两件事，验证方式完全不同。**

| | 新增（`authoring.md`） | 修改（本文件） |
| --- | --- | --- |
| 从哪开始 | 造一个新的 | 先定**根因在哪一层** |
| 验证什么 | 从零验这一个 | **验波及面** |
| 最大风险 | 造错抽象 | **改错层** + **漏验消费者** |

本文件是第三条支线：`creation-workflow.md` 管「为一个新类型造一整套」，`authoring.md` 管
「往已有套件里加一个」，本文件管「**已经存在的东西怎么改** —— 而且改完不会把别的弄坏」。

> ⚠️ **名字**：`kit-core` 是内核的旧名，2026-10-04 起是 `kits/kernel/`。
> 本文件的**现状描述**用新名，**引用历史记录**时保留旧名。
> 裁定记录（工作区 `docs/`）：`2026-10-04-T01-分发与归属-裁定.md`（分发与归属）、
> `2026-10-04-T02-类型包挂载-裁定.md`（类型包声明它组合了什么）。

## 1. 先分清：在哪儿改

**套件是复制进项目的**（见 `SKILL.md` 的安装一节），所以「改已有组件」有三个完全不同的去向，
走错要么白干，要么污染沉淀：

| 在哪改 | 影响谁 | 要不要走本流程 |
| --- | --- | --- |
| **项目副本**（`<project>/src/kits/…`） | 只影响这一支片子 | 不用走本流程 —— 也**不用留痕**（见下） |
| **技能里的套件**（`<SKILL_DIR>/kits/…`） | 影响**以后每一个**装它的人 | **要** —— 走本流程 |

判断法一句话：**下次做同类视频，还会不会想要这个改动？**

- 会 → 回技能里的套件改（**沉淀**）；
- 不会（这一支特有）→ 就在项目副本里改完拉倒。

**「会」的那一半再分两类**（T01 裁定的口径，细则见裁定记录 §6）：

| 改动的性质 | 去哪改 | 为什么 |
| --- | --- | --- |
| **缺陷**（写错了、漏了消费者、契约与实现不符） | **直接改母本对应那一份** | 它本来就是错的，没有「本片特有」这一说 |
| **创作**（这一支要的样子不一样） | **参数覆盖**，或**添加**新东西 | 覆盖不产生分叉；添加是原子操作，不会与母本冲突 |

> ### 为什么工程里的改动**不用**留痕
>
> T01 裁定 §6 把「本片独有」归进**无事发生**：不裁决、不留痕、不报警。
> 原先那层人工声明（`FORKS.md`）**已经删掉** —— 它想解决的那个问题
> （「母本那边不知道你改了什么」）现在由**机械事实**解决：更新器（`tools/update-kits.ps1`）
> 装了基线，逐字节比一下就知道哪个文件被本地动过。人工声明只会多一处会漂移、会说谎的地方。
>
> ⚠️ **但「机械比得出不同」不等于「知道它是什么」**：哈希只能证明字节不同，
> **注释措辞的差异与真正的逻辑漂移长得一模一样**（实测过一次：某副本的 `ListLayout.tsx`
> 与母本哈希不同，而差异只是注释措辞、功能逐字一致）。
> 所以**冲突**（两边都改过同一个文件）永远交给人看，工具只负责把三边摆清楚、不自动覆盖。
>
> > 提交改动前先跑一次 `-Scan`：它会告诉你「你现在改的这些东西」与母本之间是什么关系。

> ⚠️ **改动不会自动传播。** 技能里的套件改完，**已经被复制走的那些项目不会跟着变** ——
> 它们当初是复制出去的，不是共享依赖。要把更新送进去，跑**更新器**（`tools/update-kits.ps1`）：
> `-Scan` 看一眼 → 有未解决项就 `-Resolve` → `-Apply`。
> **不要**再手工整目录覆盖 —— 那会连工程里的微调一起冲掉，而那正是更新器存在的理由。

## 2. 动手前：先定根因层（症状 ≠ 根因层）

**修改流程里最常见的错误是改错层** —— 在症状冒出来的地方打补丁，根因还在，下次以另一种形状复发。

下面每一条都是这个工程里**真实发生过**的（记录在内核的 `kits/kernel/kit.md` 的验证记录里，
当时那个目录叫 `kit-core`）：

| 看到的症状 | 容易被误改的层 | 实际该改的层 |
| --- | --- | --- |
| 页脚小字比正文还大（43px > 32px） | 逐处调家具字号 | **缩放基准** —— 家具用了 `width/1080`，该改成母版的 `box.scale` |
| 浅色主题上网格看不见、暗角发脏 | 主题（换深一点的底色） | **消费方** —— `Stage` 把网格线 / 暗角色写死了，该改成 `theme.color.grid` / `color.vignette` |
| 换主题后组件颜色不变 | 主题（再试一个） | **组件的取值方式** —— 原语 import 了主题单例，该改成 `useTheme()` |
| 改了主题的某个字段，画面毫无反应 | 主题（改大一点） | **该字段缺消费者** —— 要么接上消费者，要么删掉 |
| 内容被报头压住 | 版式（把内容往下挪） | **母版的让位方式** —— `padding` 挤不开绝对定位的 `<Sequence>`，该改成 `top`/`bottom` 内容盒 |
| 内容整体下移约一个 padTop，右侧脱离安全区 | 版式的位置 | **过约束的盒模型** —— 四个 inset 遇上 `AbsoluteFill` 内置的 `width/height:100%`，必须同时置 `auto` |
| 安全区被撑到 143px | 安全区常量 | **缩放基准** —— `SafeArea` 也用了 `width/1080`，统一为 `Math.min(w, h) / 1080` |
| 长文本缩成蚂蚁 / 字号下限像没生效 | 文案 | **护栏的上下界** —— 上下界反了会**无声忽略下限** |
| 深色主题下摘要几乎读不出来 | 组件（调亮文字色） | **主题的次要文字色 + 暗角** —— 暗角叠在边角上，而报头页脚正在边角 |

**共同的模式**：症状总出现在**消费方**，根因常常在**被消费的那个约定** ——
缩放基准、取值方式、契约字段、让位方式。

所以动手前先问一句：**这个值是写死的，还是本该从别处取的？**
写死的 → 改消费方；本该取的 → 改被取的地方（多数是主题或契约）。

## 3. 波及面：谁在消费它

改之前先把消费者列出来 —— **修改的验证范围 = 消费者的集合**。

| 改这里 | 谁被波及 | 硬规则 |
| --- | --- | --- |
| `theme/**` | 该套件的每个版式、每个原语、每件家具 | **不许改版式一行**（`theme-contract.md` 第 6.3 节的 0 行改动硬指标） |
| `master/furniture/**` | 该套件的每个版式（家具与内容区不得重叠） | 位置由边距常量固定；字号用 `box.scale` |
| `master/layouts/**` | 只有这个版式 | 版式只管内容区：不重复家具、不改安全区 |
| `master/types.ts`（槽契约） | **所有**读这个槽的版式 | `required` / `overflow` / `kind` 必须与实现一致 |
| `guards/**`（在内核里） | **所有**版式 × 所有原语（护栏是全局的） | 上下界都要生效 |
| `components/**`（在内核里） | 用到它的每个场景 | 颜色 / 字族只能来自 `useTheme()` |
| **`compose.ts`**（资产声明） | 展示页的**合并视图** | 声明与目录**必须一致**：声明的来源里没有那一层 → 生成器报 WARN；自己有了那一层却还声明着来源 → 补入会失配 |
| **`kits/kernel/**`（内核）** | **所有类型包** | 见下 |

**改内核的代价最大。** 内核是每个类型包的原语 / 通用版式 / 护栏来源，改它 = 所有类型包都要重验一遍。

所以：**能在类型包里改的，不要改内核。** 只有确实属于**跨套件通用**的（排版、基础动效、布局、护栏）
才改内核 —— 而且改完要**逐个类型包**跑一遍它们的演示合成，并**重新生成展示页**
（合并视图会把内核那一层补进每个类型包的页面）。

## 4. 两条反向规则：被逼着改另一层，就说明分层错了

修改时如果发现自己「不得不」动另一层，先停下 —— 那不是要不要动的问题，是**分层错了**：

| 你正在改 | 发现必须 | 说明 | 正确做法 |
| --- | --- | --- | --- |
| 主题 | 动版式的结构（换行、换位、加元素） | 主题缺字段 | **加主题字段**，不要改版式 |
| 版式 | 写死一个色值 / 字体名 / 圆角 | 主题缺字段 | **加主题字段**，版式继续从 `useTheme()` 取 |
| 版式 | 按主题名写分支（`if (theme.name === …)`） | 主题缺字段 | 同上 —— **出现分支即证明缺字段** |
| 原语 | import 某个具体主题文件 | 原语再也不能换主题 | 只许 `theme/context` |
| 主题 | 加一个没人读的字段 | **「声明了却没人读的字段是谎话」** | 要么接上消费者，要么别加 |
| 版式 | 抄一遍报头 | 那是家具 | 家具只在母版层渲染一次 |
| 类型包 | 新建 `components/` 或 `KitShowcase.tsx` | **那是内核的层** | 那个通用件进内核；这一层由 `compose.ts` 补入 |

> 这几条都有实测来源：为了让主题层干净，一次性改掉了 7 个共用缺陷，其中三个正是
> 「声明了没人读」「消费方把颜色写死」「组件 import 主题单例」。

## 5. 回归验证：改了什么，就必须重跑什么（**本节是重点**）

**新增是从零验一个；修改是验「被波及的那些」。** 漏掉一个消费者，就漏掉一次回归。

| 改了 | 必须重跑 | 看什么 |
| --- | --- | --- |
| `theme/**` | 该套件 **× 每个主题 × 每个版式**抽帧；另做一次哈希比对 | `master/**` + `guards/**` + `components/**` **逐条一致**（版式 0 行改动） |
| `master/furniture/**` | 每个版式一张 | 家具与内容区不重叠、完全落在安全区内、字号没超过正文 |
| `master/layouts/**` | 该版式一张 + **清单类补一张末尾帧** | 从该序列本地 0 帧起算；可选槽缺省时优雅降级 |
| `master/types.ts` | **所有**消费该槽的版式 | 契约三列（`required` / `overflow` / `kind`）与实现一致 |
| `guards/**` | **全部版式 × 全部主题** | 上下界都生效、长文本没缩成蚂蚁 |
| `components/**` | 该套件的 `KitShowcase` + 用到它的版式 | 每个 prop 分支都还正常 |
| **`kits/kernel/**`** | **每个类型包的演示合成** ＋ **重新生成展示页** | 每个类型包都还出得了帧；合并视图那一页的元素墙还在 |
| **只动了 `compose.ts`** | **重新生成展示页** | 页头是否写明「元件层补自 X」；筛选按源码路径还能筛到（生成器会报 WARN 拦住缺失） |
| 只改了文案 / 演示内容 | 出这段内容的那一帧 | 有没有溢出 —— **文案也是内容，也会溢出** |

三条不许省：

1. **`tsc` 全绿不算验过。** 这个工程里三层的「全绿但错」记录分别是：组件层的插值单位混用、
   母版层的 5 个定位 / 缩放缺陷、主题层的次要文字对比度 —— **每一层都只有抽帧能抓到**；
2. **必须真的看图**，不是「渲染成功了」；
3. **改了主题就做哈希比对** —— 它是「换主题不换版式」唯一能自证的方式。

> 修改的典型失误是「**只验了改动点，没验它旁边的**」。所以改完**跑一次整组**，
> 而不是只补抽受影响的那几张。

## 6. 改完的回写

- **`kit.md` 的验证记录追加一行**：改了什么 / 跑了什么 / 结果；
- 若改动让某个「已知限制」**消失了，就把那一行删掉** —— 留着就是谎话；
- 若改动改了渲染要求（例如开始用 WebGL），更新「渲染配置档」；
- 若改动改了组件清单，更新组件表；
- 若改动改了槽或版式，同步 `master/types.ts` 的 `LAYOUT_SPECS`；
- **若改动动了原语的 props，同步 `components/specs.tsx` 的 `COMPONENT_SPECS`**（那份在**内核**里）——
  声明里的 prop 名、`display`、`demoFrame`、`tunable` 都是生成器校验的对象：对不上报 **WARN**（不一致），
  漏声明报 **NOTE**（原语视图里根本不出现它）。**这是「改坏了也看不见」最容易发生的地方**；
- **加了 / 删了 / 改名了展品，同步 `labels.ts`**（五层各一张表：元素 / 版式 / 家具 / 主题 / 场景）。
  类型包那份**只填自己那几层**，补入的层由来源那份负责。
  它只服务展示页 —— 但**缺一条不会自己响**：页面照常渲染，只是那一格退回英文。
  生成器双向校验（少一个 WARN、多一个 WARN），所以「加了元素忘了写中文名」是被接住的；
  漏的只是**这一轮没重跑生成器**这一种情况；
- **若把一个东西在内核与类型包之间搬了家，同步 `compose.ts`** —— 声明与目录必须一致；
- **回技能的改动要跑一次全量**：`tsc` + `compositions` + 该套件演示的整组抽帧；
- **重新生成套件展示 web**（`showcase/generate.ps1`）—— 展示页是「**用户看得见的那一面**」，
  而它是**活渲染**的：重跑一次约一秒，改完立刻能播着看节奏对不对，不必等一轮抽帧。
  改了元素却不重跑，用户看到的还是旧的，于是他会照着一张过期的画面提修改意见。
  生成器会自己对漏项报警（版式没场景、主题未登记、家具字段没有消费者、元件层缺失）。

## 反例清单

- ❌ 在症状出现的那一层打补丁，不问根因层
- ❌ 改主题时顺手改了版式（0 行改动硬指标立刻破）
- ❌ 改版式时写死色值 / 字体名 / 圆角，或按主题名写分支
- ❌ 改完只抽改动那一张，不抽旁边的
- ❌ 改了主题不做哈希比对就声称「版式没动」
- ❌ 在项目副本里改完，以为技能里那份也跟着变了
- ❌ 技能改完，以为已有项目会自动拿到（它们不会 —— 跑更新器，`tools/update-kits.ps1`）
- ❌ 用整目录复制去更新一个已有工程（会连工程里的微调一起冲掉；那正是更新器存在的理由）
- ❌ 手工 `Copy-Item` 装套件却**不建基线**（之后只能用 `-Adopt` 补，而它只在逐字节全等时才允许）
- ❌ 更新之后发现还有未解决项，却把这次标成「已完整接受上游」（`-Partial` 的结果按定义是部分更新）
- ❌ 改完不追加验证记录，或留着已经失效的「已知限制」
- ❌ 为了改一个类型包，直接改内核（所有类型包都被波及）
- ❌ 改了内核却不重新生成展示页（每个类型包那一页的合并视图都变了）
- ❌ 在内核与类型包之间搬了东西，忘了同步 `compose.ts`
- ❌ 在类型包里新建 `components/` 或 `KitShowcase.tsx`（那是内核的层）
- ❌ 加了主题字段却没人读（谎话字段）
