# Remotion 组件套件构建框架

把「**一个全新类型的视频需求**」变成「**一套可复用组件**」—— 拆解需求 → 定版式与槽 →
定主题与母版 → 按契约创作 → 抽帧验证；**也管已有套件的修改**，改完按波及面重跑回归。

视频制作里最慢的两件事是**写代码**和**等渲染**。本技能对两件都下手：一个类型只造一次套件，
同类视频之后只是在摆版式；每个套件带渲染配置档，并标注哪些组件昂贵。

> ⚠️ **名字**：`kit-core` 是**内核的旧名**。2026-10-04 起内核在 `kits/kernel/`，
> 类型包不再复制它（只放差异，见第一节）。本文件与各 `kit.md` 里的**验证记录**保留旧名与
> 当时的结论 —— 那是**历史**，改了就不是记录了；**现状描述**一律用新名。
> 两份裁定记录（在工作区 `docs/`）：`2026-10-04-T01-分发与归属-裁定.md`（分发方式）、
> `2026-10-04-T02-类型包挂载-裁定.md`（类型包怎么声明它组合了什么）。

## 一、核心概念

**一个套件 = 主题 + 母版 + 组件三层；但三层不必由它自己提供。**

| 概念 | 是什么 | 契约 |
| --- | --- | --- |
| **主题（theme）** | 长相：色板、字体族、字阶、安全区、间距、动效签名、图形语言 | `references/theme-contract.md` |
| **母版（master）** | 版面骨架：固定家具 + 版式变体 + 槽契约 | `references/master-contract.md` |
| **组件（component）** | 叶子视觉元素（契约原语） | `references/component-contract.md` |
| **模板（template）** | 场景 / 合成脚手架，把组件与版式组装成可渲染的东西 | `kit.md` |
| **清单（`kit.md`）** | 何时用、含什么、主题与版式清单、渲染配置档、已知限制 | — |

三层的关系：**换主题不换版式，换版式不换主题。** 母版从主题取色与尺度；组件也只能从
`useTheme()` 取色 —— 谁都不许把品牌色写死，也不许 import 某个具体主题文件。
（全系统**只有一个** `ThemeProvider`；类型包 re-export 内核那一份，不复制第二个 context。）

**`kits/kernel/` 是内核**：三层齐全（4 个主题 + 母版引擎与 6 个版式 + **19** 个原语 + 溢出护栏）。
**全系统只有这一份。**

**`kits/<类型>/` 是类型包**：只放**差异** —— 这个类型自己的主题 / 版式 / 家具 / 场景，
外加一份 `compose.ts`（**资产声明**：本套件从哪些来源补入它结构上不拥有的层）。
它**不持有原语，也不持有组件层演示** —— 那两层结构上就是内核的（类型包不可能攥着 19 个通用原语），
所以由声明补入。运行时靠它自己的 `master/MasterFrame.tsx` **适配器**把
「内核的引擎 + 本套件的家具」组合起来；调用方接口不变。

**套件是复制进项目的**（版本化源码分发），不是共享依赖；**装的时候内核与类型包一起装**
（类型包自己没有原语）。所以改动不会自动传播 —— 这一点决定了「在哪儿改」是个真问题（第五节）。

**什么进套件、什么留在调用处 —— 定层要问两件事：**

> ✅ **依据（2026-10-05 对齐，不是候选）：** 这套定层由工作区的架构基线文档给出 ——
> §2 术语（「形」拆成三个对象、简称的准确含义）・§3 **A01**（结构基线：内核＋类型包，创作项目在系统外）・
> T01 §2 术语与 §5。**两个维度不是一套互斥分类**，见下。

| 维度 | 取值 | 它回答什么 |
| --- | --- | --- |
| **① 资产类别** | 主题 · 皮 · 版式 · 母版 · 原语 · 家具 · 夹具 | 这是**什么资产** —— 决定它长什么样、怎么用 |
| **② 维护归属** | **内核**（全系统一份）· **类型包**（这个类型专属）· **项目**（这一部作品／这个工程） | **谁持有并维护它** —— 决定它住在哪、改动怎么传播 |

| 常见情形 | 资产类别 | 常见归属 |
| --- | --- | --- |
| 这类视频**每一期**都有的长相（色板 / 字族 / 字阶 / 安全区 / 间距 / 动效签名） | 主题 | 内核 / 类型包 / **项目** 都可能 |
| 常用外观的**预设描述** | 皮 | 同上 —— **项目也可以维护自己的皮** |
| 这个**类型**每一期都有的形（版式 / 家具 / 槽） | 版式 / 家具 | **类型包**（`master/**`） |
| 这个形**别的类型也要**（排版、布局、基础动效） | 原语 / 机制 | **内核**（`kits/kernel/`）—— 全系统一份 |
| **只有这一期**这样（内容、分镜表、怎么摆、具体时序值） | 内容 | **项目（调用处）** —— 不写进套件 |

⚠️ **判据是复用需求，不是类别名。** 主题 / 皮 / 版式是**资产类别**，内核 / 类型包 / 项目是**维护归属** ——
两者是**两个维度**，**别排成互斥分类**。（T08 裁的是**皮机制**的落点 `kits/kernel/skins/`，
它没有说「皮只能由内核维护」。）今天只有一个项目时，「只有这一部用」的东西默认就住项目 ——
T01 的版本化源码分发本来就允许工程副本就地改。

**简称的准确说法：共同机制集中维护，作品输入由项目持有。**
旧的「创作在外（只有值）· 形在内（写一次）· 系统只校验不持有」容易被读成
「创作项目只能填值、每段 JSX 构图都得进类型包」—— 架构基线文档 §2 **明确不这么用**，已改。
最后一行「**只有这一期**这样」的判据与反例见 `references/creation-workflow.md` 第 1 节。

## 二、何时运行

| 状态 | 动作 |
| --- | --- |
| **用户提出一个全新类型的视频需求** | **走创作流程（第三节）** —— 这是本框架的主线 |
| **要改已有的组件 / 版式 / 主题** | **改已有件（第五节）** —— 先定根因层，再按波及面重跑回归 |
| 需要套件里没有的组件 | 按第四节造；单个组件的流程见 `references/authoring.md` |
| 已有套件能直接复用 | 复用已有套件（第六节）→ 安装（第七节）→ 组装（第八节） |
| **想先看看套件 / 试不同内容和实例参数** | 从系统总览进入通用内核或类型包；自有内容与组合依赖分开。工作台逐帧试验、对照内容差异。先读 `showcase/README.md` |
| **想知道原语能调什么** | 展示页「用法」读取实际公开 Props；既有规格说明在 `components/specs.tsx`。页面控件只覆盖该演示适配器支持的参数 |
| 要换一套视觉身份（长得完全不同） | 加 / 换主题：读 `references/theme-contract.md`，**不要**改版式 |
| 只是预览 / 渲染 / 单帧 / 列合成 | **不跑本技能**，用 `remotion-studio` / `remotion-render` |
| 还没决定要做什么视频 | 先跑 `remotion-intent` |
| 要调色、加特效、做地图、上字幕 | 那是别的领域技能的事；本技能只提供骨架组件 |

### 展示页保持同步

改动套件后，运行 `showcase/generate.ps1 -Project <依赖工程>` 并检查 WARN 与 NOTE；持续开发可加 `-Watch`。收尾运行相同来源的 `-CheckFresh`，返回 0 才说明输出与来源一致。展示固定读取技能母版；Project 只借用依赖。展示失败保留成功版本，工程副本更新另走第十一节。扩展展示或处理构建问题时读 `showcase/README.md` 与 `showcase/DESIGN.md`。

## 三、创作流程（主线）

**用户提出的类型没有现成套件时，不要拿别的套件硬凑 —— 那就造，这正是本框架的主场。** 八步：

| 步 | 动作 | 产出 |
| --- | --- | --- |
| 1 | 需求拆解：这类视频每期都在讲哪几种东西 | 信息形态清单 → **用户确认（唯一强制暂停）** |
| 2 | 定槽：每个版式的槽、必填性、溢出策略 | `LAYOUT_SPECS` 条目 |
| 3 | 定固定家具：每期都在的元素 | `FurnitureConfig` 字段 |
| 4 | 定主题：给 2–3 个方向让用户用眼睛选 | `theme/<id>.ts` + 登记 |
| 5 | 创作：先主题 → 再母版 → 按需补组件 | `theme/**` / `master/**` / `components/**` |
| 6 | 造演示合成（**不可省**）：用最坏情况内容 | 该套件的 `ShowcaseScenes.tsx` 新场景 |
| 7 | 抽帧验证：`tsc` + 按版式抽帧 + **真的看图** | 验证记录 |
| 8 | 入库：`kits/<类型>/` + `kit.md` + `labels.ts` + `compose.ts` + `catalog.md` | 该类型从此可复用 |

**完整方法、每步的判据与反例见 `references/creation-workflow.md` —— 动手前读它。**

两条最容易颠倒的：

- 产物是**一套组件**，片子是顺带产物；
- **第 1 步要用户确认信息形态**，没确认不要开始写代码（那是最便宜的一道关）。

## 四、为一个新视频类型造一整套组件

第三节的八步落到具体文件时，按层拆开（顺序即第三步的第 5 步：主题 → 母版 → 组件）：

- **主题**：照 `theme/default.ts` 复制，登记进 `theme/index.ts`，跑
  `theme-contract.md` 第 6 节的三步验证。**不许改版式。**
- **版式**：加进 `master/layouts/`，槽注册进 `master/types.ts` 的 `LAYOUT_SPECS`，场景加进
  `templates/ShowcaseScenes.tsx`（这样母版演示与**所有主题**的演示都会覆盖到它）。
  ⚠️ 通用版式（cover / headline / list / stat / quote / closing）**住在内核**，不要在这里再写一份。
- **家具**：这类视频每期都在的元素 → 加进 `master/furniture/` 与 `FurnitureConfig`（用 `&` 扩展内核那份）。
- **组件**：见 `references/authoring.md`。先判断该不该做成组件（复用 ≥2 次，或这一支独有的复杂度
  值得隔离），写完**必须在演示合成里加一个场景**，然后跑第十节的验证，最后更新 `kit.md`。
  ⚠️ **叶子原语归内核** —— 新类型要的如果是一个通用件（排版 / 布局 / 基础动效），它进内核，不进类型包。
- **中文名**：五层展品（元素 / 版式 / 家具 / 主题 / 场景）各写一条进套件根的 `labels.ts`。
  它**只服务展示页**，所以不进任何运行时契约 —— 别给 `Theme` / `LAYOUT_SPECS` / `FurnitureConfig`
  加 `label` 字段。缺一条**不会自己响**（页面照常渲染，只是那一格退回英文），
  所以生成器双向校验它；但那只在你**重跑生成器**时才查得到。
- **`compose.ts`**：**资产声明**，一行 `sources: ['../kernel']`。生成器照它补入类型包缺的那两层
  （元件层 / 组件层演示），展示页的合并视图靠它成立。**工具不认识 `kernel` 这个名字** ——
  名字住在声明里，是数据不是规则。

归属规则：

- **跨套件通用**的组件 / 版式 / 主题放**内核**（`kits/kernel/`），不要复制到多个类型包里；
- **新类型专属**的主题 / 版式 / 家具 / 场景**直接建 `kits/<类型>/`**，**只放差异**；
  不要先堆进内核等以后拆 —— 那会带来两次搬迁和一次归属返工，期间还污染内核的「通用」定位。

> 这一节是 `creation-workflow.md` 的**文件级落点**；顺序、关卡与判据以那份文件为准。

## 五、改已有组件 / 版式 / 主题

**新增是从零验一个；修改验的是波及面。** 三件事：

**1. 先分清「在哪儿改」。** 套件是复制进项目的，所以：

| 只影响这一支片子 | 下次做同类视频还会想要 |
| --- | --- |
| 在**项目副本**里改 —— 改坏了重新复制一次 | 回**技能里的套件**改，沉淀下来 |

**技能改完，已经被复制走的项目不会跟着变** —— 要把更新送进工程，跑**更新器**（第十一节）。
它靠**基线**分清「母本改了」与「你为这一支片子改过」，所以不会冲掉工程里的微调。
更细的三分类（缺陷 → 直接改母本；创作 → 参数覆盖或添加；本片独有 → 不用留痕）
见 `docs/2026-10-04-T01-分发与归属-裁定.md` 的第 6 节。

**2. 先定根因层 —— 症状 ≠ 根因层。**
症状总出现在**消费方**，根因常常在**被消费的那个约定**：缩放基准、取值方式、契约字段、让位方式。
动手前先问：**这个值是写死的，还是本该从别处取的？**

| 症状 | 常被误改的层 | 实际该改的层 |
| --- | --- | --- |
| 浅色主题上网格看不见 | 主题（换底色） | **消费方** —— `Stage` 把网格色写死了 |
| 换主题后组件颜色不变 | 主题（再试一个） | **组件的取值方式** —— 该走 `useTheme()` |
| 改了主题字段画面毫无反应 | 主题（改大一点） | **该字段缺消费者** —— 接上，或删掉 |
| 页脚小字比正文还大 | 逐处调家具字号 | **缩放基准** —— `width/1080` 该改 `box.scale` |
| 内容被报头压住 | 版式（往下挪） | **母版的让位方式** —— `padding` 挤不开绝对定位的 `<Sequence>` |

**3. 改完按波及面重跑 —— 漏一个消费者就漏一次回归。**

| 改了 | 必须重跑 |
| --- | --- |
| `theme/**` | 每主题 × 每版式抽帧 + 哈希比对（`master/**`+`guards/**`+`components/**` 逐条一致） |
| `guards/**` | **全部版式 × 全部主题** |
| `components/**` | 该套件的 `KitShowcase` + 用到它的版式 |
| **`kits/kernel/**`（内核）** | **每个类型包**的演示合成 ＋ 展示页重建（代价最大，能在类型包里改就别改内核） |

**`tsc` 全绿不算验过 —— 必须真的看图。**

**完整流程、症状→根因对照表、回归范围表见 `references/modification-workflow.md`。**

## 六、复用已有套件

**可用性以 `references/catalog.md` 为准** —— 它只列**已沉淀**的套件（真实存在、抽过帧的）。

1. 查 `catalog.md` 顶部的「已沉淀」表：目标类型是否已有套件？
2. **有** → 安装（第七节）→ 组装（第八节）；
3. **没有** → 走第三节的创作流程造一套；
4. 有 `BRIEF.md` 时直接用它的 `genre` 与受众，**不要重新问**。

常见类型各自的**版式构成起点**（信息形态 → 版式）列在 `catalog.md` 的
「常见类型的版式构成参考」一节 —— 那是**创作起点建议，不是可用性承诺**。

**内核**自带 4 个主题（`default-dark` / `paper-seal` / `bubble-pop` / `neon-terminal`）。
**先问用户要哪一套长相，而不是先问要什么颜色** —— 换主题不用改版式一行。

## 七、安装

**把套件复制进项目**，不要从共享 npm 包 import。装的是**内核 + 该类型的包**（两份）：

```bash
cp -r "<SKILL_DIR>/kits/kernel"  "<project>/src/kits/kernel"
cp -r "<SKILL_DIR>/kits/<类型>"  "<project>/src/kits/<类型>"
```

Windows PowerShell：

```powershell
Copy-Item "<SKILL_DIR>\kits\kernel"  "<project>\src\kits\kernel"  -Recurse
Copy-Item "<SKILL_DIR>\kits\<类型>"  "<project>\src\kits\<类型>"  -Recurse
```

⚠️ **内核不能省。** 类型包只有差异，原语与组件层演示都在内核里 —— 只装类型包那一份会编译不过。
（类型包根的 `compose.ts` 声明了这件事，展示页生成器照它补缺；但**运行时**是真 import，
所以两份都要在。）

⚠️ **装的时候顺手把基线建起来**（用更新器，别只用 `Copy-Item`）：

```powershell
pwsh -File "<技能目录>\tools\update-kits.ps1" -Project "<工程根>" -Install
```

它做的事和上面两条复制命令一样，但**记下了一份基线**。基线是「当初接受上游时，这些文件长什么样」——
**母本以后改了**，更新器就靠它分出「母本改了（可以安全重刷）」与「你为这一支片子改过（绝不能碰）」；
**没有基线，这两件事长得一模一样**（哈希只能证明「不同」）。
手工 `Copy-Item` 装出来的副本没有基线，之后只能用 `-Adopt` 补 —— 而它**只在副本与母本逐字节全等时才允许**
（那一刻「落后」与「改过」重合，重建才可证明无损）。

**为什么复制而不是共享依赖**：

- 视频组件几乎总要为这一支片子改；共享包是僵的
- 复制进来后可以自由改，改坏了重新复制一次即可
- 复制**不改变 Studio 能看到什么**（源码在你自己的工程里，不是藏在一个包里）——
  至于某一格能不能编辑，取决于**那一格的形状**，不取决于它是复制的还是被 import 的；
  判据见 `references/component-contract.md` §3
- 复制是**版本化**的：母本侧每一次改动都有提交记录，工程侧取得的是**可独立修改的源码快照**

**安装后必做**：

1. 选一个主题：`theme/index.ts` 里挑 `ThemeId`，或照 `theme/default.ts` 复制改一份 ——
   色板、字族、字阶都在那一个文件里，改它就是改整套长相（见 `theme-contract.md`）；
2. 把套件自带的演示合成注册进 `src/Root.tsx`（见 `kit.md` 的注册示例），它们是验证载体；
   主题演示用 `THEME_IDS.map(...)` 批量注册，一个主题一个合成；
3. 跑一次验证（第十节），确认装进来的东西在你的环境里能编译、能出帧。

## 八、组装

组装 = 在 `<Sequence>` 里摆**版式**（不是裸组件）。版式已经在母版里定好了槽与溢出策略。

```tsx
<MasterFrame theme={getTheme('paper-seal')} furniture={{masthead: {...}, footer: {...}}}>
  <Sequence from={0} durationInFrames={90} premountFor={30} name="Scene 1">
    <CoverLayout kicker="今日必读" title="主标题" meta="2026-09-19" />
  </Sequence>
</MasterFrame>
```

约定：

- **家具只在母版层写一次**（报头 / 页脚 / 进度），场景里不要再写一遍；
- **每个 `<Sequence>` 都给 `premountFor`**，否则素材加载会抖；
- **`name` 硬编码**，它是 Studio 时间线里的标签；
- 需要逐场景并排、改一个时长自动顶开后面时，用 `<TransitionSeries>`；
- 逐实例的尺寸与时间**内联写在调用处**。⚠️ 但两者在 Studio 里**不是同一种结果**：
  **尺寸**（`fontSize = 96` 这类静态值）内联了就可编辑；**时间**（`delayInFrames`）今天内联了也变灰 ——
  它要进 `interpolate` 的 input range，而那会让**整格**变成计算值（2026-10-05 实测，见
  `references/component-contract.md` §3）。

## 九、渲染

按套件的渲染配置档设置 flag —— 见 `references/render-profiles.md`。要点：

- 迭代期先低质量出片，只在交付时用高质量：`--scale` / `--crf` / `--jpeg-quality`；
- **WebGL 类组件**（效果、3D、地图）渲染时必须 `--gl=angle`，并建议 `--concurrency=1`；
- 并发不是越高越好，用 `npx remotion benchmark` 实测你这台机器的最优点，别猜。

## 十、验证（改完必跑）

每个套件自带演示合成，它们把三层各摆了一遍。这是验证载体，不是给用户看的成品。

```bash
npx tsc --noEmit                                  # 类型与 props
npx remotion compositions                         # 入口能否解析、合成是否注册成功
npx remotion still KitShowcase    out/k-1.png --frame=30     # 组件层
npx remotion still MasterShowcase out/m-1.png --frame=30     # 母版层（按版式抽帧）
npx remotion still ThemeShowcase-paper-seal out/ps-1.png --frame=30   # 主题层
```

- `tsc --noEmit` 与 ESLint **抓不到**渲染期问题（动画根本没动、插值单位不匹配、WebGL 没开、
  字体没加载、对比度不足、家具压住内容）；
- 抽帧是唯一可靠的确认手段：**看抽帧，不看 Studio 播放**；
- **按版式抽帧**（每个版式一张），不是按场景抽；清单类版式再补一张末尾帧；
- **改了主题或加了主题 → 每个主题每个版式各抽一张**，并做一次哈希比对：
  加主题前后 `master/**` + `guards/**` + `components/**` 必须逐条一致（版式 0 行改动）。
  完整命令见 `references/theme-contract.md` 第 6 节；
- **改了已有件 → 按第五节的波及面重跑整组**（不是只补受影响的几张）；
- 改了组件就重跑，并把结果记回 `kit.md`。

**实战证据**：内核（当时还叫 `kit-core`）首次验证时 `tsc --noEmit` 全绿，但 `TextReveal` 在渲染时
抛错——`translate` 插值写成了 `['0px 100%', '0px 0px']`，第二个分量把百分比和像素混用。
**只有抽帧能抓到这类错误。** 母版层与主题层同样各有一次「全绿但看图才发现」的记录，见
`master-contract.md` 第 2 节与 `references/theme-contract.md` 第 6.2 节。

## 十一、更新：母本改了之后，怎么进到工程里

**更新器** `<技能目录>\tools\update-kits.ps1`。它判的就是 T01 裁定 §7 那张三态表 ——
而**判得出这件事的前提是基线**（第七节安装时建立的那一份）。

```powershell
pwsh -File <技能>\tools\update-kits.ps1 -Project <工程根>                  # 只报告（默认，一个字节都不写）
pwsh -File <技能>\tools\update-kits.ps1 -Project <工程根> -Apply           # 应用（有未解决项时**拒绝**）
pwsh -File <技能>\tools\update-kits.ps1 -Project <工程根> -Apply -Partial  # 只应用无歧义的那一部分
pwsh -File <技能>\tools\update-kits.ps1 -Project <工程根> -Resolve all -Decision keep-local
pwsh -File <技能>\tools\update-kits.ps1 -Project <工程根> -Rollback latest  # 收尾一次被中断的事务
```

| 判定 | 含义 | 默认动作 |
| --- | --- | --- |
| **仅母本修改 / 首次母本新增** | 母本改了、工程这边没动过 | **写** —— 这是唯一会自动覆盖的情形 |
| **仅本地修改 / 本地独有 / 本地删除** | 你为这一支片子做的 | **一个字节都不碰**，只列出来 |
| **两边都改了、结果不同** | 冲突 | 报出来，**绝不自动覆盖**，用 `-Resolve` 裁决 |
| **母本删除** | 母本不要它了 | **不替你删**；要跟随就 `-Resolve … -Decision accept-upstream` |
| **上游重新引入** | 这个路径删过，母本又放回来了 | 报出来；默认**不**按「新增」写回（那会抹掉有意删除的历史） |
| **同名同内容** | 两边各生了一个一样的 | 保留文件、**待确认接管** —— 字节一致不自动改变归属 |

四条要记住的：

1. **默认不写。** 存在未解决项时 `-Apply` 直接**拒绝**（退出码 3）；`-Partial` 才写无歧义的那一部分，
   而且结果会标成**部分更新** —— 「文件没被覆盖」不等于「冲突解决了」；
2. **计划是固定的。** `-Scan` 把目标内容存下来，`-Apply` 用的就是那一份；母本之后又变 → **拒绝**，
   除非 `-Pinned` 明确表示「就用旧快照」；
3. **失败能恢复。** 写入前备份、写后验证（默认跑工程自己的 `tsc --noEmit`，**写前写后各一次**：
   写前就失败说明「本来就坏」，不因它回滚；写前通过而写后失败 → **自动回滚**）。
   进程被杀留下的半成品，下次运行会被拦下（退出码 6），用 `-Rollback` 收尾；
4. **工程侧不用留痕。** T01 裁定 §6：本片独有的改动属于「无事发生」——
   更新器自己就算得出「这个文件被本地动过」，不需要人工声明。

**改了母本之后的标准动作**：`-Scan` 看一眼 → 有未解决项就 `-Resolve` → `-Apply`。
退出码：`0` 完成 · `1` 有可更新 · `2` 用法错误 · `3` 需要裁决 · `4` 计划过期或来源状态无效 ·
`5` 验证失败并已回滚 · `6` 需要恢复。

**基线住在哪**：`<工程>\.kit-origin\<套件>\` —— `.origin.json` 清单 ＋ `baselines/gNNNN/` 基线内容
＋ `plans/<计划 ID>/`（计划、暂存的目标内容、事务日志、`before/` 备份）。
它是**本机的工作记录**，不进版本库（工程自己 `.gitignore` 掉）；换机器用 `-Adopt` 重建。
代价如实说：一个工程的基线约 **518 KB**（内核 366 KB ＋ 类型包 100 KB 的副本）。

**明确不做**：不自动合并、不做语义冲突判断、不识别重命名（按「删除 ＋ 新增」报）、
不自动回填母本、不自动删除工程文件。
